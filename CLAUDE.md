# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

AI-powered home shopping product research platform. Users upload product files (PDF, PPTX, DOCX, images), the system extracts product info via Gemini Vision API, then synthesizes comprehensive market research reports targeting Japan and Korea markets.

## Commands

```bash
npm run dev      # Start dev server (localhost:3000)
npm run build    # Production build
npm run lint     # ESLint
```

No test framework is configured.

## Architecture

### Two-Phase Async Processing Pipeline

1. **Extract** (`POST /api/analyze`): Gemini Vision extracts product metadata from uploaded files → returns immediately
2. **Synthesize** (`POST /api/analyze/synthesize`): Triggered in background by extract phase → runs Brave Search + Rakuten API queries → Gemini synthesizes a 13-section research report → saves to Supabase

### Key Data Flow

```
File Upload → Supabase Storage → Gemini Vision (extract)
  → Brave Search + Rakuten (parallel queries) → Gemini (synthesize)
  → Supabase DB (research_results) → Report UI (13 sections)
```

### Broadcast Calendar (Phase A — read-only)

- Daily JST 01:00 cron (`16:00 UTC` → `app/api/cron/daily-broadcasts/route.ts`) scrapes yesterday's broadcasts from Shop Channel (`shopch.jp`) and QVC Japan (`qvc.jp`) via cheerio.
- Daily JST 02:00 cron (`17:00 UTC` → `app/api/cron/qvc-monthly-refresh/route.ts`) re-scrapes the QVC programme guide for the **previous month + current month** (Phase 1-B) via `lib/broadcasts/qvc-monthly.ts::refreshQVCMonthlyRange`. The QVC site exposes ~2 months of schedule data; this catches slots published ahead of time and corrects any backfill gaps. Upserts are idempotent (channel,air_date,start_time conflict key), so daily reruns are cheap. ShopCh forward slots (today..+`SHOPCH_FORWARD_DAYS`, default 14) are scraped by `lib/broadcasts/shopch-forward.ts::refreshShopChForwardRange`, wired into the JST 02:00 `qvc-monthly-refresh` cron. Both forward paths run future-only reconciliation (`lib/broadcasts/reconcile.ts`) that deletes rescheduled/cancelled forward slots — strictly `air_date > today_jst`, never touching archived rows.
- Read API: `GET /api/broadcasts?from=YYYY-MM-DD&to=YYYY-MM-DD[&channel=shopch|qvc]` (max 62-day range).
- Admin recovery: `POST /api/broadcasts/refresh` with `{date}` or `{from,to}` (max 7 days), `Bearer ${CRON_SECRET}`.
- UI: `/[locale]/broadcasts` — month grid + sticky right-side `UnifiedDayDetailPanel` (covers all 10 channels with schedule data: QVC, ShopCh, and 8 OA channels in one list with channel + category chip filters). Below the calendar, a separate `HistoricalBroadcasts` panel offers free-text history search across **all 10 channels** (QVC + ShopCh from `broadcasts` table, 8 OA from `historical_broadcasts`). `/api/broadcasts` accepts `?search=` (program_title ilike); the panel calls both endpoints in parallel and merges results client-side. No date coupling — empty until the user enters a search term or picks a channel chip. (btops was removed 2026-05-17 — site closed.)
- Module layout: `lib/broadcasts/{types,fetch,shopch,qvc,persist,index}.ts`.
- Fixture-based parser tests: `npm run test:broadcasts-parsers`. Live integration: `npm run test:broadcasts-live`. Operational diagnostic: `npm run verify:broadcasts`. One-shot 7-day backfill: `npm run backfill:broadcasts -- --days=7`.
- Phase B PoC (QVC only): `broadcasts.product_ids text[]` is populated from each slot's `data-products` attribute; `qvc_products` caches OG metadata (name, image, price text, video) fetched from `qvc.jp/product.{id}.html`. The daily cron auto-enriches new IDs; manual run via `npm run enrich:qvc-products`. Shop Channel product detail requires JS rendering (Playwright) and is deferred.
- Category whitelist (Phase 1-C, `lib/broadcasts/category-filter.ts` + `channel_categories` table): every QVC + ShopCh slot gets a `category`. QVC reads from `qvc_products.category` (extracted by the product-page parser via JSON-LD or breadcrumb); ShopCh runs a Gemini batch classifier on `program_title + description` against a 5-item whitelist. **Policy (2026-05-18 v3): all slots are still persisted regardless of category, but the calendar UI hides non-whitelist QVC/ShopCh slots at display time — even with `全カテゴリ` selected, and even in the `全チャンネル` view.** Category chips render only when `channelFilter` is `qvc` or `shopch` (hidden when "all channels" is selected, since a union of per-channel chips would be incoherent). In-UI whitelist lives in `components/broadcasts/UnifiedDayDetailPanel.tsx::CATEGORIES_BY_CHANNEL` (mirrors the admin-editable `channel_categories` table; RLS: read=member, write=admin). OA channels in `historical_broadcasts` have no whitelist and pass through unchanged. **Update (2026-06-03, fail-open): a slot with NO category (null/unclassified) is now SHOWN — only a KNOWN non-whitelist category is hidden. Forward QVC slots arrive un-enriched (category null) and must not be hidden as if non-whitelist. The gate lives in `lib/broadcasts/whitelist-gate.ts` (extracted from UnifiedDayDetailPanel).**
- Discovery soft penalty (`lib/discovery/recent-broadcast-penalty.ts`): candidates whose `qvc.jp/product.{id}.html` URL matches a product aired on QVC within the last `BROADCAST_RECENT_LOOKBACK_DAYS` (default 30) get `BROADCAST_RECENT_PENALTY` (default 10) subtracted from `tvFitScore`. Soft only — never excludes. Applied post-curation in the daily-discovery crons. Other channels (shopch + the 13 brave site:search channels) have no product_id linkage and are silently unaffected.
- Competitor-trend boost (Phase 3-C, `lib/discovery/competitor-trend-boost.ts`): the top `HOT_CATEGORY_TOP_N` (default 5) categories aired on QVC + ShopCh within the last `HISTORICAL_LOOKBACK_DAYS` (default 30) are derived from `broadcasts.category`. Each candidate whose `name` or `category` contains any keyword (composite categories split on `・/／`) from a hot competitor category gets `HISTORICAL_CATEGORY_BOOST` (default 5) added to `tvFitScore` and a `[他局トレンド: …]` annotation on `tv_fit_reason`. Applied after the penalty step in both daily-discovery crons. `historical_broadcasts` will be unioned in once its OA-channel whitelist is configured.
- Fit-weighting layer (2026-05-18, same file): the per-category boost above is reshaped by the avg `competitor_fit_analyses.fit_score` for that category (lookback = `HISTORICAL_LOOKBACK_DAYS`, min sample = `FIT_MIN_SAMPLES`, default 3). Below the sample threshold the baseline boost is unchanged. Above it the multiplier is `1 + (avg - 50) / 25` clamped to `[0, 2.5]` — avg ≤ 25 cancels the boost entirely (the user already judged this category low-fit despite competitor airings); avg 50 is neutral; avg ≥ 87.5 amplifies 2.5×. The `[他局トレンド: …]` annotation gains a ` 適合度:NN点(n=M)` suffix when weighting was applied, so the cause is traceable in the saved row. The fit analyses themselves are written from `/api/broadcasts/analyze-fit` when the operator clicks "自社販売適合度を分析" on a calendar slot — accumulating curatorial judgement that now bends the next day's discovery scoring.
- Crawl observability (`lib/historical-crawl/runs.ts` + `/admin/historical-crawl` page): every `daily-historical-broadcasts` cron execution writes a row to `historical_crawl_runs` (admin-only RLS) with per-channel `rowCount` / `durationMs` / `error`. The admin dashboard surfaces the last 30 runs and a 7-day per-channel median; row counts dropping below 50% (red) or 80% (amber) of the median flag the channel for operator review. Treat this as the gate before adding category filtering or AI competitive analysis downstream.
- `historical_broadcasts.start_time time` (Phase 1-D, nullable): added so future parsers / re-audits can fill per-slot start times without another schema change. Of the 7 OA channels currently scraped, only senobura exposes a per-slot start time (parsed from `.onair-time`); the others stay NULL. The existing UNIQUE(channel, air_date, product_name) is left as-is — if a channel later exposes multiple distinct slots for the same product/day, the UNIQUE can be widened then.
- Competitive snapshot archival (2026-05-19, `docs/superpowers/specs/2026-05-19-competitive-snapshot-archival-design.md`): whitelist-matching slots are enriched at scrape time with a per-product detail snapshot in `broadcast_products` (name/image/price/original_price/discount_rate/sale_label/in_stock_at_capture/brand). QVC video is archived to AWS S3 + CloudFront by a separate `archive-videos` cron (JST 04:00 + 10:00) — `ffmpeg -c copy` streams the QVC m3u8 into a multipart MP4 upload. Storage key: `videos/{channel}/{air_date}/{start_time}--{broadcast_id_short}.mp4`. ShopCh video uses the same `archive-videos` cron — per-program m3u8 derived from `programId` (= `air_date + start_time`) at `https://www.shopch.jp/m3u8/prog/{programId}/{programId}_jwplayer.m3u8`. CloudFront origin is public (no auth/cookies/Referer); a 403 means the object doesn't exist for that programId. Slots are marked `video_status='queued'` only when the slot JSON's `pgmMovie` is non-null (otherwise `deferred`). Verified 2026-05-27. UI: `BroadcastListItem` shows ▶ when `archived_video_s3` is set; clicking opens `BroadcastVideoModal` with the video + per-product list. Admin observability: `/admin/archive-status`. S3 storage via AWS SDK + CloudFront for egress. Env vars: `VIDEO_ARCHIVE_AWS_REGION`, `VIDEO_ARCHIVE_AWS_ACCESS_KEY_ID`, `VIDEO_ARCHIVE_AWS_SECRET_ACCESS_KEY`, `VIDEO_ARCHIVE_AWS_BUCKET`, `VIDEO_ARCHIVE_BASE_URL` (CloudFront distribution URL), `NEXT_PUBLIC_VIDEO_ARCHIVE_BASE_URL` (same, client-readable). The `VIDEO_ARCHIVE_AWS_*` namespace is intentional — it avoids collision with `lib/s3.ts` (product images) which uses bare `AWS_S3_*` against a different bucket + IAM key. Bucket should match the CloudFront origin; objects are public-read (no signed URLs in v1).
- **Archive storage class — the whole catalogue is GLACIER_IR as of 2026-09-06** (`scripts/promote-archive-storage-class.ts`, `npm run promote:archives`). A lifecycle rule used to drop every object into DEEP_ARCHIVE one day after upload; it was corrected to Glacier Instant Retrieval on 2026-08-25, but that only governs NEW objects, so 5,051 objects (3.24 TB) stayed cold. They were readable only because a 14-day restore had been requested around 2026-08-28 — and **a restore does not move an object**: it leaves the original in Deep Archive and parks a temporary copy beside it, so `StorageClass` still reads `DEEP_ARCHIVE` and a `Restore` header carries the expiry. When that lapsed (2026-09-10) UI video playback would have started failing in the way `storage-class.ts` describes — a cold object answers a CloudFront HEAD with full metadata, so nothing looks broken until the GET returns AccessDenied. `CopyObject` onto the same key is what actually moves an object, and 5,004 were promoted that way (QVC 2,378 + ShopCh 2,626, zero failures). It is server-side, so it costs nothing in transfer and needs no in-region host; no object exceeds 5 GiB (largest 2.47 GB) so a plain copy covers every one. **Copying FROM Deep Archive requires a live restore** — 46 QVC objects had none and failed with `InvalidObjectState`, which is what that error means here. Consequence for the analysis drain: reading a live restore copy was free, whereas GLACIER_IR bills ~$0.03/GB retrieval, so a ShopCh drain now costs ~$90 more than it would have during the restore window. That was the accepted trade for removing the expiry deadline (~$25 one-off early-deletion against the Deep Archive 180-day minimum, ~$10/month more storage).
- **Reading the archive back** (`lib/broadcast-intel/audio-extract.ts`): `BROADCAST_INTEL_READ_VIA` selects the path — `cdn` (default, the public CloudFront URL playback uses) or `s3` (GetObject against the bucket). **The default must stay `cdn`**: the bucket is in `ap-northeast-2`, so S3 is free only to a reader in that region and costs ~$0.126/GB elsewhere — more than CloudFront's ~$0.114 — and the `analyze-broadcast-audio` cron runs on Vercel, outside the region. Set `s3` only where the reader shares the region; that is what makes a 3 TB ShopCh drain cost ~$0 of transfer from a Seoul instance instead of ~$345 from a laptop. Both paths produce byte-identical audio (verified 2026-09-02).
- Archival operations: production cron (`/api/cron/archive-videos`) handles the daily flow automatically (JST 04:00 + 10:00). For manual recovery (catch-up after env outage, force-archive a backlog, etc.) use `npm run daily:archive` which chains `backfill:broadcast-products` (enriches whitelist-matching slots — `brand_name`, `broadcast_products` rows, `video_status='queued'`) + `drain:archive-queue` (loops `archiveOne` at concurrency 4 until empty). Same workflow the cron uses internally, just executed locally. Typical full drain is ~3-5 min per ~25 slots.
- Phase C (time-slot analytics) still builds on this `broadcasts` table.

### Discovery TV Channel Source (extends home_shopping)

- Discovery pipeline tags candidates from 15 Japanese TV-shopping channels as a tier-1 priority signal so they appear above other candidates on `/[locale]/analytics/discovery/home`.
- Sources: existing `broadcasts` table for shopch + qvc (Phase A); Brave `site:` search for the other 13 channels listed in `docs/検索参考サイト (2).xlsx`.
- Persistence: `discovered_products.tv_channel_source` (comma-joined alphabetical slugs, nullable) + `tv_tier int` generated column (0=TV, 1=other) for sorting.
- Ordering: `runStage1` in `lib/discovery/orchestrator.ts` partitions candidates after scoring; API and UI both sort by `(tv_tier ASC, tv_fit_score DESC)`.
- Env knobs: `TV_CHANNEL_BRAVE_BUDGET` (default 50) caps daily Brave site:-search calls; `TV_CHANNEL_BROADCAST_WINDOW_DAYS` (default 30) sets the broadcasts lookback.
- Channel registry: `lib/discovery/tv-channels.ts` lists all 15 with slug/name/siteQuery/scraped flags. Only `scraped: true` channels (shopch, qvc) read from `broadcasts`; the rest go through Brave site: search.
- **Analysis queue balancing** (`lib/broadcast-intel/{priority,queue}.ts`): the seed pool is balanced per **channel + category** (`analysisBalanceKey`), not category alone — QVC's ~2-minute clips and ShopCh's ~1-hour programmes are different media, and a category-only key let QVC take every round in a shared category. Analysed counts come from a `BROADCAST_INTEL_ANALYZED_LOOKBACK_DAYS` window (default 30), so the preamble cost is constant and a category worked through months ago becomes due again. Half the candidate pool is drawn oldest-first (`OLDEST_CANDIDATE_POOL_SHARE`): newest-first alone pinned the window to the last few days once daily arrivals outpaced the promote rate, leaving the backlog unreachable by the cron.
- **Derive channel sets from `lib/discovery/tv-channels.ts`, never restate them.** `lib/intelligence/{backfill,insights}.ts` each kept a hand-written copy that had fallen four channels behind (`ropping`, `kachimo`, `kaidoki`, `uranoura`), so their products were silently rejected — no canonical identity, no evidence, and no log line saying so. Exclusions come from `EXCLUDED_DISCOVERY_SLUGS` for the same reason. Note `insights.ts` additionally accepts `"oa"`, the fallback `mapBroadcastAnalysisEvidence` uses when a broadcast row has no channel.
- **Two-registry split — don't conflate**: `lib/discovery/tv-channels.ts` (15 channels) drives discovery candidate sourcing. `lib/broadcasts/channel-style.ts` (10 channels = qvc + shopch + 8 OA, with ropping + kantv being added 2026-05-21) drives the broadcasts calendar UI. The OA list is a strict subset whose schedule pages we can actually scrape; the remaining 4 (kachimo / kaidoki / ichiban / rakurakum) live only in discovery via Brave because their schedule pages don't exist or aren't parseable.

### Product Selection Pipeline (2026-05-25)

- 4-stage operator workflow on top of the existing `sourced` feedback: **선택됨(selected) → 소싱중(sourcing) → 방송예정(scheduled) → 종료(closed)**. `closed_reason ∈ {aired, dropped, postponed}`. Spec: `docs/superpowers/specs/2026-05-24-product-selection-pipeline-design.md`; plan: `docs/superpowers/plans/2026-05-24-product-selection-pipeline.md`.
- Tables (migration `2026-05-24_product_selections.sql`):
  - `product_selections` — id, `discovered_product_id` FK (cascade), `status`, `owner_id` (RESTRICT) / `assignee_id` (SET NULL), `broadcast_id` FK (SET NULL), closed_{reason,at,by,note}, {sourcing,scheduled,closed}_note. Partial unique `(discovered_product_id) WHERE status != 'closed'` enforces "at most one active selection per product"; re-selection after close is allowed. CHECK constraints: `scheduled_requires_anchor` (broadcast_id OR scheduled_note), `closed_requires_reason` (reason + closed_at).
  - `product_selection_events` — append-only audit log; event_types: `created | status_changed | assignee_changed | broadcast_linked | broadcast_unlinked | closed | reopened | note_updated`. `is_system=true` marks cron-emitted events. No UPDATE/DELETE policy (immutable).
- RLS Group A: SELECT for all authenticated (viewer included for read-only board); INSERT/UPDATE for member|admin via separate `ps_insert` + `ps_update` policies (no DELETE for any role except service). `pse_select` open, `pse_insert` member|admin only.
- Phase 0 unification (entry points into the pipeline):
  - Both `/discovery/home` AND `/strategy/expansion` cards render `FeedbackButtons` — strategy expansion previously lacked it; this was the structural gap closed in Phase 0.
  - `lib/strategy/fresh-search-persist.ts::persistStrategyFreshSearch` runs during strategy generation (called from `lib/workflows/md-strategy.workflow.ts::persistFreshSearchStep`). Every `fresh_search` / `research` rec gets a stub `discovered_products` row in a synthetic `discovery_runs` session (status `running` → `completed` on success, `failed` on bulk-insert error so `reconcileStaleDiscoveryRuns` can clean it). The strategy doc JSONB then carries `discovered_product_id` for every rec uniformly. **The `prevent_recent_duplicate_discoveries` BEFORE INSERT trigger may silently skip URLs already in another recent session — the helper follows up with a SELECT recovery pass so `idByUrl` always returns an id.**
- Selection creation/auto-close inside the existing feedback handler (`app/api/discovery/feedback/route.ts`):
  - `sourced` ON → if no active selection exists for that product, INSERT one with `status='selected'`, `owner_id=auth.uid()`, emit `created` event.
  - `sourced` toggled OFF by the same user → if the active selection is still in `selected` stage, auto-close with `closed_reason='dropped'` and emit `status_changed` + `closed`. Selections already advanced past `selected` are preserved — operator has invested work into them.
- API endpoints (all `requireUser(['member','admin'])` except reads which include `viewer`; all use `auth.sb` so RLS applies):
  - `GET /api/selections` — board grouped by status. Filters `?scope=mine_owned|mine_assigned`, `?assignee=<id|all>`, `?includeClosed=1` (closed last 7 days only). `?q=` is currently a no-op (PostgREST cannot filter on embedded resource via supabase-js — v1 trade-off; filter client-side).
  - `GET /api/selections/counts` — active count by stage + total. Powers the nav badge.
  - `POST /api/selections/:id/move` — stage transition with optimistic lock (`UPDATE ... WHERE id=? AND status=<expected_from>`, 409 on miss). VALID transitions: `selected → {sourcing, closed}`, `sourcing → {selected, scheduled, closed}`, `scheduled → {sourcing, closed}`, `closed → {}` (use `/reopen`). `scheduled` requires `broadcast_id` OR `scheduled_note`; `closed` requires `closed_reason`.
  - `POST /api/selections/:id/assign` — assignee change. Emits `assignee_changed` with from/to.
  - `POST /api/selections/:id/reopen` — `closed → sourcing`, clears `closed_*` fields; 409 if another active selection has since taken over the same product.
  - `PATCH /api/selections/:id/note` — inline edit on `sourcing_note` / `scheduled_note` / `closed_note`. 400 on invalid field, 404 if selection not found.
  - `GET /api/selections/:id/events` — timeline read (viewer allowed).
  - `GET /api/selections/match-broadcast?productName=&channel=&from=&to=` — broadcast candidate search with Jaccard-style name similarity. Returns `{ suggestions: top-6 score > 0.15, others: top-30 score ≤ 0.15 }`.
- UI:
  - `/[locale]/analytics/pipeline` — server page, `auth.sb` data fetch, 4-column kanban with `@dnd-kit` drag-drop, optimistic move + revert on 409/500. Cards include thumbnail, name, price/TV-fit, stage-specific pill (broadcast slot / note / closed reason), owner→assignee footer. `?focus=<selection_id>` deep-link scrolls + ring-highlights the card for 1.5s. Korean stage labels (선택됨/소싱중/방송예정/종료) hardcoded in `KanbanBoard.tsx` for v1.
  - Card menu (`components/pipeline/CardMenu.tsx`): 이력 보기 (`EventsTimelineModal`), 원본 상품 보기, 종료 처리 / 다시 소싱으로 (context-sensitive). **`window.prompt` is a v1 placeholder for the closed-reason picker — replace with shadcn dialog in Phase 2.**
  - Drag-to-scheduled opens `BroadcastMatchDialog` (`components/pipeline/BroadcastMatchDialog.tsx`) — searches `broadcasts` by name + channel + date range, or accepts a free-text `scheduled_note` for slots the table does not yet contain.
  - `PipelineStatusChip` (`components/pipeline/PipelineStatusChip.tsx`) renders on discovery + strategy cards when an active selection exists. Click → `/analytics/pipeline?focus=<id>`. Discovery cards get `active_selection` via the server-side join in `/api/discovery/today`; strategy cards fetch via a single bulk `/api/selections` call inside `DiscoveredProductsHero`'s `useEffect`.
- Navigation: market group gains a 4th member at `/analytics/pipeline` (after broadcasts/discovery/strategy). Navbar shows the active-selection count badge via `/api/selections/counts` (server-fetched, graceful 0-on-error). Viewer is on the allowlist (`lib/auth/route-permissions.ts::VIEWER_ALLOWED_PATH_PREFIXES`).
- Cache invalidation:
  - `lib/selections/cached.ts::invalidateSelectionsAfterMutation(source)` revalidates tags `selections:board` + `selections:counts` on every write (feedback handler, all `/api/selections/*` mutations, cron auto-advance).
  - `lib/discovery/cached.ts::MUTATION_TAGS` includes the selection tags too — discovery-side mutations refresh the board chip data on existing cards.
- Daily cron `/api/cron/pipeline-auto-advance` (JST 03:00 = UTC 18:00, `vercel.json`): closes `scheduled` selections whose linked `broadcast.air_date < today_jst` with `closed_reason='aired'`, `closed_at = ${airDate}T12:00:00+09:00`, `closed_by=null`, `is_system=true`. Emits `status_changed` + `closed` events. Defensive `WHERE status='scheduled'` on the UPDATE. Manual-note (`broadcast_id IS NULL`) scheduled selections are NOT touched — operator must close them by hand.
- Backfill: the migration ports existing `discovered_products.user_action='sourced'` rows whose original author is recoverable from `product_feedback` (with `user_id IS NOT NULL` guard) into new `product_selections` rows with `status='selected'`, plus a `created` event marked `is_system=true` with a `Backfilled from ...` note. ### Data Intelligence Foundation (2026-08-29)

Background accumulation only. The system continuously collects, normalizes and scores competitor signal into reusable evidence; **product recommendation, research and screenplay generation stay on demand and are never triggered by this layer.** Spec: `docs/superpowers/specs/2026-08-29-on-demand-data-intelligence-pipeline-design.md`; plan: `docs/superpowers/plans/2026-08-29-data-intelligence-foundation.md`.

- **Evidence contract** (`lib/intelligence/{types,evidence,repository}.ts`): every atomic fact is an `evidence_items` row carrying subject, predicate, value, `evidence_class` (`verified` / `source_claim` / `proxy` / `inferred` / `internal_input`), source identity and `observed_at`. `value_state` separates a known value from `unknown` / `not_applicable` — an unobserved number is never stored as 0. Dedupe is a SHA-256 over the canonical draft (`evidenceDedupeKey`) against `unique (dedupe_key)`, so re-running a backfill is idempotent. The key covers `unit` and `evidence_class` and normalizes `observed_at` before hashing — without those, JPY and USD hashed alike, a `verified` measurement collapsed onto a `proxy` signal, and the same instant spelled `+00:00` vs `Z` minted a duplicate. **Changing the key definition orphans every existing row's key: run `npm run rekey:intelligence-evidence -- --apply` before the next backfill, or it will re-insert everything.**
- **Run telemetry** (`lib/intelligence/pipeline-run*.ts`): seven crons record a normalized `data_pipeline_runs` row. This is **derived observation, best-effort, and must never gate the work** — a recorder failure is caught and logged while the primary flow continues. The domain tables (`discovery_runs`, `historical_crawl_runs`, `broadcasts.analysis_status`, `video_status`) remain the source of truth for job state and mutual exclusion. `insight_refresh` is the one documented exception: it has no domain table, so `20260830110000` gives it the same sliding-window duplicate trigger the other cron paths use.
  - **A pipeline row is a projection of its domain row and must never be worse than it.** `historical_crawl_runs` saying `completed` while `data_pipeline_runs` said `failed` for the same execution is the bug this rule prevents.
  - **Status vocabulary**: `succeeded` = did what it set out to do with no failures; `partial` = genuinely degraded; `failed` = produced nothing. Routine backpressure — a deferred slot with no video, a queued retry, an unresolvable category — is carried in `counts`, never promoted to a status. Readiness renders `partial` as `degraded` (amber) and an in-flight run as `running`; only an outage is red.
  - **Orphans**: a killed function leaves `running` behind forever. `reapOrphanedPipelineRuns` sweeps rows whose heartbeat is older than 30 minutes, called as a preflight from the insight-refresh cron (the same shape as `recoverStaleDownloading` in the archive path). The insight scan resumes only from a run in a terminal status, so an orphan can never hand over a cursor.
- **Backfill** (`lib/intelligence/backfill.ts`, `npm run backfill:intelligence`): bounded and cursor-resumable, dry-run by default, `--apply` to write. Only `discovered_products` rows with `source = 'tv_channel'` from connected channels are eligible.
- **Canonical linking runs nightly, not only by hand** (`lib/intelligence/link-discovery-products.ts::linkDiscoverySessionProducts`): both discovery crons link the session they just produced, as a budgeted optional stage via `runOptionalStage`. Before this, `product_source_links` was written only by the CLI backfill while the readiness denominator is the newest discovery session — so canonical-link and category coverage were pinned at 0% however much evidence existed. Identity is telemetry-grade: this stage may never cost a night's candidates, so it degrades rather than throws. It resolves `normalized_category` from the `discovered_category_normalization` **cache only** — never the Gemini normalizer the CLI uses, which is not affordable inside the save budget — and stores null when a raw category is uncached. **A raw value must never land in `normalized_category`**: it would make the coverage metric read as satisfied while the stored values are wrong. `resolveExactCanonicalProduct`'s repair path fills the category in on a later run once the cache warms.
- **Insight refresh** (`lib/intelligence/{insights,refresh-insights}.ts`, cron `/api/cron/refresh-intelligence-insights`, JST 05:00): incrementally turns active evidence into `insight_snapshots`, each linked to the exact evidence rows it consumed via `insight_snapshot_evidence`. `unique (insight_type, subject_type, subject_id, formula_version, input_until)` makes a repeated write a no-op rather than a second row, and the cron floors `input_until` to a 5-minute quantum (`refreshInsightsCutoff`) so two invocations of one trigger compute the same window and actually collide there. That quantum is defence in depth, not the lock — the trigger is — so a pair straddling its boundary costs one redundant snapshot, not a corrupted cursor. Bounded by `BUDGET_MS = 240_000` against a 300s `maxDuration`, checked in both the scan loop and the candidate loop. A category insight aggregates the category's own population — every analysed broadcast in it within `INTELLIGENCE_CATEGORY_WINDOW_DAYS` (default 30), capped at `CATEGORY_INSIGHT_MAX_BROADCASTS` — not the broadcasts that happened to fall in the scan page that made it due; without that, `sampleSize` and `dominantShare` described an arbitrary slice while being labelled the category's, and two snapshots were not comparable. **The scan cursor is saved only after the snapshots are written, and never when the run stops at its deadline** — re-doing a window is safe (`candidateIsEligible` skips a subject that already has a snapshot at this cutoff), whereas advancing past unwritten subjects loses them until the scan wraps.
- **Readiness** (`lib/intelligence/readiness.ts` → `components/pipeline/DataReadinessDashboard.tsx` on `/[locale]/analytics/pipeline`): replaces the old static Sankey with DB-derived status. Measured ~1.6s per render against a 5,200-row archive (down from ~3.1s): the analysed side is read whole and intersected in memory rather than chunking every archived id back at `broadcast_speech_analyses`. It is still an unbounded archive scan on a `force-dynamic` page and grows with the archive — a server-side aggregate is the real answer if it becomes a problem. `INTELLIGENCE_READINESS_SOURCES` hardcodes the `(source_type, job_type)` pairs — **adding a cron means adding it there too, or its status silently never appears.** The discovery entries additionally require `external_run_id` to be the `discovery_runs.id`; changing that format breaks coverage.
- **Verification**: `npm run verify:intelligence-foundation` is read-only and is the completion gate (`docs` Task 10). As of 2026-09-05 it passes 8/8 — category coverage reached 100% once `linkDiscoverySessionProducts` started running nightly inside both discovery crons, which is what it was waiting for.
- **All four plans dated 2026-08-29 are implemented**: the foundation, `stored-only-product-finder` (2026-09-04), `grounded-screenplay-workflow` and `controlled-knowledge-inputs` (both 2026-09-05). See their sections below.

### Controlled Knowledge Inputs (2026-09-05)

The two ways new information enters the ledger, and the one way it leaves. Plan: `docs/superpowers/plans/2026-08-29-controlled-knowledge-inputs.md`.

- **Evidence is REVOKED, never deleted** (`evidence_items.revoked_at / revoked_by / revocation_reason`, `20260829160000`). A deleted row would break the RESTRICT from `knowledge_snapshot_items` and silently rewrite what a past recommendation is recorded as having read. **Every consumer filters `.is("revoked_at", null)` in the QUERY**, not just in memory: the product finder, both screenplay readers, the canonical brief loader, and `refresh-insights.ts::applyActiveFilters` (the single chokepoint both insight readers pass through). A partial index covers exactly that predicate.
- **`product_recommendation_runs.mode` widened to `stored_only | supplemented`.** That CHECK is where "did anything reach the internet" is answered; widening it was a schema change on purpose. `parseProductFinderQuery()` still only produces `stored_only` — the mode comes from the runner's `options`, which is single-sourced onto the row and the snapshot.
- **Supplemental research** (`lib/intelligence/supplement/`, `POST /api/product-finder/runs/[runId]/supplement`): the only path that may call an external provider. The gap enum is closed in the type AND the database CHECK — there is deliberately no `actual_competitor_revenue`. Research WRITES evidence and the re-rank READS it back through the same database-only runner; nothing ranks an in-memory search result. **A total provider failure returns the ORIGINAL run id, writes nothing and creates no new ranking** — an outage must not cost the operator the result they already had; one failed gap out of several is `partial`. Classification never flatters its source: a seller's sales figure is `source_claim` even on their own official page, review counts are `proxy`, and only a value read off a fetched official page is `verified`.
- **`safe-fetch.ts` is the only code that fetches a URL a third party chose.** Every hostname is resolved before every hop, every resolved address must be publicly routable (loopback, link-local incl. cloud metadata, private, CGNAT, IPv4-mapped), redirects are manual, and the body is capped as it streams. The residual DNS-rebinding window is documented in the file rather than papered over.
- **Excel import** (`lib/intelligence/imports/`, `app/api/intelligence/imports/*`, `/analytics/data-management`): four stages — upload → mapping → validation → apply — with nothing reaching the ledger until apply. Deterministic, no model: header matching is an alias table (JA/KO/EN) an operator confirms. **Blank is unknown, explicit 0 is zero, unmapped is neither** — carried from `defval: null` on the sheet read through `parseCurrency`'s `null | undefined` return to `importRowEvidence` skipping both. `Number("")` is 0, and that is precisely how a data-entry gap becomes a business result. `product_name` is the only required mapping; performance columns are optional.
- **Only an `active` canonical product may be ranked or scripted.** `canonical_products.status` is `active | merged | inactive`, and for a while nothing read it. A `merged` row is the ledger having already decided two rows are one product, so ranking both puts the same product on screen twice, each holding half of its evidence — the pair scores *worse* than either would whole. `lib/product-finder/candidates.ts` filters `status = 'active'` (which is also what lets a category query use the partial index); `lib/screenplay/product-brief.ts` refuses a non-active product with 409 rather than following `merged_into_id`, because a merge target is a different product with different evidence and swapping it in silently would produce a script whose recorded subject is not the one that was asked for. Pinned by a static assertion in `test:product-finder-candidates`.
- **Matching is conservative**: an exact product code with an existing source link wins; a normalised name match is accepted only when UNIQUE; an ambiguous row fails for review. Merging two real products because their names normalise alike would attach every later fact about either to a product that is half of each, undetectably.
- **Rollback revokes and requires a reason** (3–500 chars). A test asserts `.delete()` appears nowhere in the apply path. `e2e:intelligence-import` proves the property that matters: after a rollback the profit disappears from a NEW ranking while the past run's knowledge snapshot still names every row it read.
- **Private storage** (`intelligence-imports` bucket, `20260829161000`): owner-scoped by `storage.foldername(name)[1]`, no INSERT policy — uploads go through the server route with service credentials, because a client that could write directly could choose a path under someone else's prefix. NOTE: `ALTER TABLE storage.objects` fails from the SQL editor ("must be owner of table objects", see `2026-05-26_storage_lock_product_files.sql`) but policies apply cleanly through the Management API.
- **The profitability axis** stops being `unknown` only once an import with cost/revenue columns is applied — `gross_profit_jpy` is the predicate it reads.
- **Tests**: `test:controlled-input-schema`, `test:supplemental-provider-contract`, `test:supplemental-research-run`, `test:supplemental-research-view`, `test:intelligence-import-storage`, `test:intelligence-workbook`, `test:intelligence-import-routes`, `test:intelligence-import-apply`, `test:intelligence-import-view`; `e2e:supplemental-research` and `e2e:intelligence-import` run separately so the two halves can be released independently. Both E2Es inject providers rather than calling Brave/Rakuten — the adapters have their own contract test, and a live call would make the gate flaky and spend quota per run.

### Grounded Screenplay Workflow (2026-09-05)

Every screenplay records what it was written FROM, before it is written. Plan: `docs/superpowers/plans/2026-08-29-grounded-screenplay-workflow.md`.

- **One entry point.** `lib/screenplay/start-generation.ts::startScreenplayGeneration` is the only way to start a generation; a static test (`npm run test:screenplay-unified-entry`) pins that `generateScreenplay(` has exactly one production caller (the workflow). `scripts/complete-recommendation-flow.ts` used to call the generator directly and insert the version itself — that row had no compliance check, no context, no snapshot and no claim links, and nothing on it said so. **`start()` from `workflow/api` only works inside the DevKit's compiled Next.js runtime** (a bare tsx process gets `WorkflowRuntimeError: 'start' received an invalid workflow function`), so the CLI now creates the screenplay row and tells the operator to start generation from the app. The `runId` is minted in the entry service, never in the workflow body: a body is replayed on retry, and both the context and its knowledge snapshot are unique on it.
- **Generation context** (`lib/screenplay/context/`, table `screenplay_generation_contexts` from `20260829150000`): fact pack + reference broadcasts + pattern status + outline + demo plan + the knowledge snapshot naming every piece of evidence behind them, persisted BEFORE prose. A refine inherits its base's context (facts, references, pattern, snapshot) and only regenerates the structure plan; inheritance breaks when the linked canonical product changes or the brief's own values change (compared on values, not a timestamp). A refine adopts the canonical product its base recorded — the `screenplays` row carries no such link.
- **`pattern_status` enumerates every absence reason** (`disabled` / `no_category` / `off_whitelist` / `under_sampled` / `timed_out` / `failed` / `applied`). `loadCategoryPattern`'s null carried all five negative meanings at once and the workflow resolved them to a console line, so a version generated six weeks ago was unexplainable. `lib/screenplay/context/pattern-result.ts::loadPatternResult` is the status-carrying entry point; `loadCategoryPattern` stays as the raw loader.
- **Fact usage follows evidence class, mechanically**: `verified`/`internal_input` → `direct` (may be stated), `source_claim` → `attributed_only` (must be attributed), `proxy`/`inferred` → `planning_only` (**never spoken on air**). One documented override: `notes` is our own input but carries research hypotheses from `buildProductBriefFromRows`, so it is pinned to `planning_only`. A blank brief field produces **no evidence row** — it goes into `missing`, and every gap becomes an explicit prohibition in `forbiddenClaims`.
- **Structure plan** (`structure-plan.ts`): Zod-validated, `basis` derived from the pattern status (never self-reported by the model), runtime shares normalised only from a sum within 0.85–1.15 (outside that the plan is unfinished, and scaling would invent structure), fact keys outside the pack dropped rather than rejected, required demos landing exactly once.
- **Claim grounding** (`lib/screenplay/grounding/`): the classifier's status is a proposal; the evidence decides. Major claims (numeric-with-unit, efficacy, superlative) are detected deterministically, so anything the classifier skipped becomes `needs_review` — a classifier that throws degrades to needs_review, never to silence. A generated version becomes `current_version_id` / `ready` only after claim links are persisted.
- **Copy guard** (`copy-guard.ts`): reads admin-only `broadcast_transcripts` **in memory only**, to ask whether OUR output contains a 30+ character run of a competitor's. What is reported is the offending passage of our own script plus which broadcast it hit. It is on the `test-broadcast-intel-guard.ts` allowlist for exactly that reason — nothing read there reaches a prompt, a response or the UI.
- **Gemini stages**: `screenplay_structure` and `screenplay_grounding` are separate cost stages from `screenplay_generation`. Folding either into the drafting stage would make the drafting stage's per-script cost wrong whenever the other changed.
- **Tests**: `test:screenplay-context-schema`, `-fact-pack`, `-reference-broadcasts`, `-structure-plan`, `-context-build`, `-unified-entry`, `-claim-links`, `-context-view`; `npm run e2e:grounded-screenplay` covers four entry paths against the live DB. The E2E does NOT generate prose (see above) — every property it asserts belongs to the context and the grounding.

## Key Conventions

- **Every Gemini call records what it consumed** (`lib/gemini-usage.ts` → `gemini_usage` table, `npm run report:gemini-cost`). Attribution is by stage, and usage is recorded **before** any post-response throw — a MAX_TOKENS truncation bills for the full output allowance and returns nothing, so recording after the throw hides the most expensive kind of call. `thinking_tokens` is tracked separately because the screenplay generator pairs Pro with HIGH thinking, which bills at the output rate and never appears in the response text. Recording is best-effort and must never throw into a caller. When adding a Gemini call site, record it too — the alternative is what happened in 2026-09: a ~$100 bill of which only the one instrumented path (~$18) could be explained.
- **Gemini model selection is per stage** (`lib/gemini-models.ts`): `modelForStage("<stage>")`, never a bare `GEMINI_FLASH` at a call site. One shared constant across ~47 sites meant every stage carried the same price and capability, so transcription could only get cheaper by making screenplay generation worse at the same time. `GEMINI_MODEL_<STAGE>` overrides one stage without a deploy. **Move a stage off its default only on measured output** — `broadcast_analysis` runs on `gemini-3.5-flash-lite` because a three-slot A/B showed it matching Flash on act coverage (100/100/100%) at 60% less; `gemini-2.5-flash-lite` is 89% cheaper and was rejected because its acts stop a fraction into the programme, so `MIN_ACT_COVERAGE` rejects them and the slot retries after its CloudFront egress is already spent.

- **i18n**: All UI text via next-intl. Translation files in `messages/ja.json` and `messages/ko.json` (default locale: ja). Research output is in Japanese.
- **UI**: shadcn/ui (base-nova style) + Tailwind CSS 4 + Lucide icons. Components in `components/ui/`.
- **Path alias**: `@/*` maps to project root.
- **Vercel deployment**: Function timeouts configured in `vercel.json` (synthesize: 300s, analyze: 120s, recommend: 60s). Daily cron at 9 AM UTC for data refresh.
- **Server Actions**: body size limit set to 50MB for large file uploads.
- **Auth (added 2026-05-13)**: Three roles — `admin`, `member`, `viewer` — gated by Supabase Auth via `@supabase/ssr`. Code reached from a user request must use `lib/supabase/server.ts::getServerClient()` for queries and `lib/auth/require-user.ts::requireUser([roles])` at the top of every API route. `getServiceClient()` is reserved for cron, workflow steps, and other non-user-initiated paths — it bypasses RLS. Internal server-to-server fetches (e.g. `/api/analyze` → `/api/analyze/synthesize`, `/api/discovery/enrich/[id]` → `/worker`) authenticate via `Bearer ${CRON_SECRET}` and `hasInternalSecret()`. RLS is the last line of defence — when adding a new table, also add a Group A (TXD, viewer-readable) or Group B (internal, member/admin-only) policy. See `docs/superpowers/specs/2026-05-13-auth-and-tiered-access-design.md`.
  - **Page components must `redirect()` on auth failure, not `return auth.error`** — `auth.error` is a `NextResponse` which is valid in API routes but rejected by Next.js's Page component build check. Pattern: `if ("error" in auth) redirect(localePath(locale, "/login"))`. API routes (`app/api/.../route.ts`) keep using `return auth.error`.
  - **`viewer` route allowlist**: viewers are redirected to `/analytics/products` for any path not in `lib/auth/route-permissions.ts::VIEWER_ALLOWED_PATH_PREFIXES`. When adding a new viewer-readable page, extend that array (currently `/analytics/products`, `/guide`, `/analytics/pipeline`). Note a viewer on an allowlisted page still sees only what RLS grants them — on `/analytics/pipeline` the kanban's `discovered_products!inner` join yields no rows and the readiness panel is skipped entirely.
  - **A derived table inherits the strictest grade among its sources.** If a wider grade is wanted, narrow the derivation — do not widen the policy. `20260830100000_intelligence_access_grades.sql` exists because the intelligence tables shipped as `using (true)` while copying rows out of member-only `discovered_products` and `broadcast_speech_analyses`. `scripts/test-intelligence-evidence-predicates.ts` pins which predicates may cross that boundary.
  - **A Group B derived table whose every writer is service-role may omit write policies** — that is the intended shape, not an oversight. Do not add a member write policy just to make a script run; run it with the service client.
  - **Unvetted third-party text does not reach the UI.** `data_pipeline_runs.error_summary` holds raw `err.message` from Gemini / S3 / Brave, so the column is revoked from `authenticated` and the dashboard renders our own `error_code` instead. A column privilege is used rather than a narrower select list because it survives a later edit to that list.
- **Paging: use `lib/supabase/paginate.ts::selectAllPages`, and never set a page size at or above `db-max-rows`** (measured 1,000 on 2026-09-03). A paging loop exits on a short page, so a page size equal to the cap works only by accident and one equal to a *lowered* cap truncates silently on the first page — no error, just a wrong number. The helper carries the `maxRows` ceiling that throws instead of returning a short answer; this project has been bitten by silent truncation repeatedly (exclusion lists missing two thirds of their codes, a dashboard totalling 1,000 of 6,000).
- **`server-only` import + tsx smoke compatibility**: lib files that you intend to directly import from a `scripts/test-*.ts` smoke script (run via `tsx --env-file=.env.local`) must NOT include `import "server-only"` — the package throws at module load when not running under Next.js's bundler alias, so tsx fails immediately. Rely on `getServiceClient` (uses `SUPABASE_SERVICE_ROLE_KEY`) as the server-side guard instead. Files that are only ever imported via Next.js route handlers can keep the import. Example: `lib/strategy/fresh-search-persist.ts` deliberately omits it; `lib/discovery/cached.ts` keeps it because no smoke imports it directly.
- **Per-user analyze rate limit** (Phase 4): `lib/research/analyze-rate-limit.ts` caps `/api/upload` at `ANALYZE_MAX_INFLIGHT_PER_USER` (default 3) concurrent analyzing rows and `ANALYZE_MAX_DAILY_PER_USER` (default 20) uploads per rolling 24h per user. Admin role bypasses. Override via env if a member team needs higher throughput.
