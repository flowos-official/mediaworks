## 🌅 매일 아침 (평일 08:30 이후, 약 10-20분)

### Step 1. 발굴 결과 확인

**URL**: `/ja/analytics/discovery/home` (기본 홈쇼핑)

매일 자동으로 생성된 **30개 신상품 후보**가 표시됩니다:
- 08:00 JST/KST → ホームショッピング 발굴 자동 실행
- 08:30 JST/KST → ライブコマース 발굴 자동 실행

상단에 다음 정보:
- 🟢 **완료** 배지 + 실행 시간
- `30/30 件` (목표 대비 실제 수)
- `ソーシング済み: N` (과거 누적)

### Step 2. 30개 카드 리뷰 (1-2분/카드)

각 카드에 다음이 포함됨:
- 🖼️ **썸네일** (Rakuten 이미지)
- 🏪 **楽天 배지** + **제품명** + **tv_fit_score** (100점 만점)
- 💰 가격, ⭐ 리뷰 평점+개수, 🛒 판매자
- 🏷️ **TV実績** / **探索** 배지
- ⚠️ broadcast tag (경쟁사 방송 이력 있으면)
- 💡 **TV適合性** 노랑 박스 (왜 홈쇼핑에 적합한지 AI 설명)

### Step 3. 빠른 피드백 (한 카드당 2-5초)

**4개 버튼 중 하나 클릭**:
- ✅ **ソーシング済み** (녹색) — "이 상품 소싱할 것" → 향후 발굴에서 **영구 제외**
- ⭐ **関心あり** (주황) — "검토 가치 있음" → 학습에 양성 신호
- ❌ **却下** (빨강) + 모달 이유 선택 → 해당 URL/브랜드 **rejected_seeds** 등록
- 🗑️ **既にあり** (회색) — "이미 가지고 있는 상품" → 영구 제외

**토글**: 같은 버튼 다시 클릭 → 해제.

## 🔍 관심 상품 심화 분석 (필요 시)

### Step 4. "深掘り" 클릭

### Step 5. C 패키지 Drawer 확인

버튼 클릭 시 카드 하단 drawer 확장:
- 🏭 **제조사 정보** + 공식사이트 + 연락처 힌트

- 📋 **MOQ 힌트** (있는 경우)
- 🎬 **TV 방송 스크립트 초안** (복사 가능)
- 🔥 **SNS 트렌드** 신호 (high/medium/low/none)

### Step 6. 拡大戦略 / ライブ戦略 생성

카드의 **📈 拡大戦略を作成** / **📡 ライブ戦略を作成** 버튼 클릭:

- 2개 버튼:

**Case B: 深掘り 완료됨** → 바로 전략 페이지 이동

### Step 7. 전략 페이지에서 생성 시작

`/ja/analytics/strategy/expansion?seedId=<UUID>` 자동 이동:
- **userGoal** 텍스트박스에 자동 pre-fill (제품명 + 참조 URL)
- **price帯** 도 pre-fill
- **拡大戦略を分析** 클릭 → Gemini 7 skills 순차 실행 (goal_analysis / product_selection / channel_strategy / pricing_margin / marketing_execution / financial_projection / risk_contingency, ~60-120초)

결과:
- **신상품 실제 데이터 기반 맞춤 전략** (가격/마진/채널/리스크 분석)
- AI 분석 근거: 기존 `product_summaries` (TV 판매 실적) + seed 제품 데이터 + SNS 트렌드
- 전략 저장 후 나중에 재조회 가능 (`/analytics/strategy/expansion/[id]`)

## 🧠 データインテリジェンス基盤の運用（管理者）

このパイプラインは、収集済みの商品・放送情報を正規化し、出典と観測時刻を持つエビデンスおよびインサイトとして継続的に蓄積します。商品推薦、Research、取扱商品の選定、放送台本は、利用者が必要なときに保存済みデータを使って生成するオンデマンド成果物です。バックフィルやインサイト更新が、これらの成果物を自動生成することはありません。

最近のデータについて、書き込み前に対象件数を確認します。

```bash
npm run backfill:intelligence -- --since=2026-08-01 --limit=200
```

`write=false`、sourceごとの読取行数、予定エビデンス数、要確認カテゴリーを確認してください。反映するときだけ `--apply` を追加します。

```bash
npm run backfill:intelligence -- --since=2026-08-01 --limit=200 --apply
```

1回の実行はsourceごとに200行が既定で、`--limit` は最大2,000行まで指定できます。出力の `nextCursor` が文字列の場合は、同じ `--since` と `--limit` にその値をそのまま渡して再開します。`nextCursor` が `null` になれば、その期間の処理は完了です。

```bash
npm run backfill:intelligence -- --since=2026-08-01 --limit=200 --cursor='<nextCursor>' --apply
```

反映とインサイト更新の後、読み取り専用の検証を実行します。

```bash
npm run verify:intelligence-foundation
```

検証では、additive migration、最新のpipeline試行、canonical link、最近のアクティブ商品のカテゴリー網羅率、エビデンス件数、インサイトとエビデンスリンク数の一致、known/non-known値の整合性を確認します。`rawActive` は最新の成功Discoveryセッションにあるアクティブ候補全体、`eligible` は現在のQVC・Shop Channel・接続済みOA source範囲でバックフィル可能な候補数です。放送分析の実測カバレッジも表示しますが、推薦や台本の生成件数は合格条件ではありません。

パイプライン画面の状態は次の意味です。

| 状態 | 意味 |
| --- | --- |
| 正常 | 最新の成功実行がsource別の許容時間内にある |
| 一部劣化 | 最新試行が部分完了。処理は動いているが確認が要る |
| 実行中 | 最新試行が進行中で、heartbeatが新しい |
| 期限超過 | 成功履歴はあるが許容時間を超えている |
| 失敗 | 最新試行が失敗、または30分以上heartbeatのない実行中。過去の成功では隠さない |
| 未実行 | 新しい正規化runがない、またはその処理をまだ実行していない |

根拠の重複キー定義を変更した場合は、次のバックフィルの前に一度だけ再計算を実行します。実行しないと、同じ事実が新しい行として二重に入ります。書き込みなしで差分を確認してから `--apply` を付けます。

```bash
npm run rekey:intelligence-evidence
npm run rekey:intelligence-evidence -- --apply
```

インサイト更新はJST 05:00の定期実行で自動的に動きます。上のバックフィルは、過去データを取り込むときや障害から復旧するときの手動操作です。

分母がない割合は `0%` ではなく `—` と表示します。推薦、Research、取扱商品選定、台本が0件でも、まだ依頼されていないだけならパイプライン障害ではありません。

### ShopCh 放送分析の一括処理（ソウルEC2）

ShopChは1本あたり約1.16GB（57分）で、3.1TB全体をローカルにダウンロードすると転送費だけで約$345かかります。バケットは `ap-northeast-2` にあるため、同一リージョンのEC2で実行すれば転送費は0になります。

```bash
# 1) 復元（Bulk、48時間、約$26）
npm run restore:archives -- --channel=shopch --category=コスメ --tier=Bulk --days=7 --apply

# 2) 完了確認
npm run restore:archives -- --channel=shopch --category=コスメ --status

# 3) ソウルEC2でドレイン
bash scripts/drain-shopch-ec2.sh
```

3のスクリプトはリージョンを確認し、`ap-northeast-2` でなければ実行を拒否します。誤ってローカルで実行し$345を使うことを防ぐためです。必要なのはインスタンスロールの `s3:GetObject` 権限と、リポジトリ直下の `.env.local` です。

ドレインスクリプトは各カテゴリの最初のバッチで `--reset=cold_storage` も実行します。復元前にcronが拾って `cold_storage` で諦めたスロットは試行回数を使い切ってキューから外れており、このリセットがなければ復元後も分析されないままです。リセットは `--channel` と `--category` の両方でスコープされるため、ドレイン中のカテゴリ外には及びません。

**復元完了前にドレインを開始しないこと。** まだ解凍されていないスロットは `cold_storage` としてスキップ記録が残り、分析されないままバックログだけが消化されます。

作業後は**インスタンスを必ず停止または終了**してください。アイドル状態でも秒単位で課金されます。

## 19. 商品ファインダー（蓄積データ基準）

`/analytics/product-finder` は**すでに蓄積された証拠だけ**を読んで商品を順位づけます。新規検索を行わないため実行に追加費用は発生せず、結果は同じ根拠でいつでも再現できます。

### 5つの評価軸

| 軸 | 何を見るか | 根拠 |
|---|---|---|
| 市場需要 | 他局の放送回数、直近の放送、レビュー数 | 代理指標 |
| 自社適合 | 指定価格帯への適合、社内粗利率 | 社内入力がある場合のみ |
| 収益性 | 貢献利益 | **社内原価データがある場合のみ** |
| 競合余地 | 競合の放送が少ないほど高い | 代理指標 |
| 放送適合 | 分析済み参考放送の量 | 推論 |

各軸には**確認済み / 代理指標 / データなし**のバッジが付きます。同じ60点でも、社内原価から出た60点と放送回数から推定した60点は別物であり、バッジがその差を示します。

### 収益性が空になる理由

`判断資料不足` は「利益がゼロ」ではなく、**「計算できる社内データがない」**という意味です。貢献利益は自社の原価からのみ算出し、競合が広告で述べた売上は自社の粗利ではないため決して代入しません。

社内原価はExcel取込機能（次フェーズ）から入ります。それまでこの軸が全商品で空欄なのは正常です。

### 競合の売上が表示されない理由

競合が「累計10万台突破」と述べた場合、それは**外部主張（source_claim）**として保存され、実売数には昇格しません。公式の出典が直接示した数値でない限り、売上・販売数としては扱わない方針です。

### 結果の読み方

- **総合指標**は収益性を除く4軸の加重平均です。収益性は性質の異なる値なので混ぜず、判明している場合は**並び替えで先に**適用されます。
- **証拠カバー率**が低いほど順位の確度は下がります。30%未満は`確度: 低`と表示されます。
- **不足しているデータ**は隠さず列挙します。画面から消えた軸は「無関係」と読まれてしまうためです。
