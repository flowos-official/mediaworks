# 온디맨드 데이터 인텔리전스 파이프라인 설계

- **작성일:** 2026-08-29
- **상태:** 설계 결정 승인 완료, 문서 검토 대기
- **대상 프로젝트:** MediaWorks
- **대상 소스:** 현재 연결된 QVC Japan, Shop Channel, OA 계열 데이터만
- **핵심 결정:** 데이터와 인사이트는 백그라운드에서 축적하고, 제품 추천과 대본은 사용자가 요청할 때만 생성한다.

---

## 1. 요약

MediaWorks의 파이프라인은 상품을 자동으로 다음 단계로 이동시키는 퍼널이 아니다. 시스템이 자동으로 해야 하는 일은 경쟁사 상품, 방송, 자막, 판매 관련 공개 신호와 자사 입력 데이터를 지속적으로 수집·정규화·분석해 **재사용 가능한 근거와 인사이트를 준비하는 것**이다.

제품 추천과 대본 생성은 이 지식을 소비하는 별도의 온디맨드 기능이다. 사용자가 요청하지 않으면 추천, 리서치, 대본을 자동 생성하지 않는다.

기본 소비 모드는 저장 데이터 전용이다. 저장 데이터가 부족하거나 오래되었더라도 시스템이 몰래 외부 검색을 실행하지 않는다. 사용자가 명시적으로 `추가 조사`를 선택한 경우에만 부족한 항목을 보강하고, 그 결과를 출처·확인 시점·근거 유형과 함께 저장해 이후 요청에서 재사용한다.

```
[자동·지속 실행]
QVC / Shop Channel / OA
  → 원본 관측
  → 정규화·상품 연결
  → 근거 원장
  → 인사이트 스냅샷
  → 품질·최신성 관리

                    ↓ 요청 시 조회

[온디맨드]
제품 찾기 → 저장 근거 기반 후보 비교·추천
대본 만들기 → 상품 근거 + 유사 경쟁 방송 패턴 기반 생성

[명시적 선택]
추가 조사 → 부족한 항목만 외부 보강 → 근거 저장 → 결과 재생성
```

## 2. 승인된 제품 결정

다음 결정은 브레인스토밍 과정에서 사용자와 합의했다.

1. **자동화 범위**
   - 자동: 데이터 수집, 정규화, 근거 추출, 인사이트 갱신, 품질 관리.
   - 수동 요청: 제품 추천, 상세 리서치, 대본 생성.
   - 금지: 후보가 생겼다는 이유로 추천·리서치·대본을 연쇄 자동 생성하는 동작.

2. **검색 정책**
   - 기본: 저장된 데이터와 인사이트만 사용.
   - 선택: 사용자가 `추가 조사`를 요청할 때만 부족하거나 오래된 항목을 외부 검색.
   - 추가 조사 결과는 일회성 프롬프트 재료로 버리지 않고 근거 원장에 축적.

3. **추천 목표**
   - 경쟁사에서 인기 있는 상품 자체가 아니라, **우리 회사가 판매했을 때 이익을 낼 가능성이 높은 상품**을 찾는다.
   - 자사 이익·원가·성과 데이터가 없으면 이익을 만들어내지 않는다. 이 경우 시장 기회도와 방송 적합도를 제공하고 수익성은 `판단 자료 부족`으로 표시한다.

4. **경쟁사 판매 데이터의 한계**
   - 공개 검색으로 경쟁사의 실제 매출·판매수량을 항상 알 수 있다는 전제를 두지 않는다.
   - 공식 수치, 판매자 주장, 방송·리뷰·랭킹 같은 대리 신호, 시스템 추론을 구분한다.
   - 대리 신호를 실제 판매량이나 매출로 표시하지 않는다.

5. **자사 데이터**
   - 자사 데이터는 선택 입력이다.
   - 초기 엑셀은 현재 보유한 상품 기본정보 수준만 있어도 허용한다.
   - 매출, 수량, 원가, 수수료, 이익 열이 있을 때만 해당 지표를 추가 활용한다.
   - 자사 데이터가 없어도 시장 근거 기반 제품 찾기는 동작해야 한다.

6. **소스 범위**
   - 현재 연결된 QVC Japan, Shop Channel, OA 계열 데이터의 품질과 연결을 먼저 완성한다.
   - 신규 경쟁사·마켓플레이스 확장은 이번 설계 범위가 아니다.

7. **대본 시작점**
   - 추천 상품, 엑셀 등록 상품, 사용자가 직접 입력한 상품 모두 대본 생성의 시작점이 될 수 있다.
   - 추천 기능과 대본 기능은 같은 지식 계층을 공유하지만 서로 종속되지 않는다.

## 3. 현재 상태와 문제 정의

### 3.1 유지할 수 있는 현재 자산

프로젝트에는 다음 기반이 이미 존재한다.

- 경쟁 방송과 상품 수집 크론.
- `discovered_products` 기반 후보 풀과 TV evidence·C package.
- `broadcasts`, `historical_broadcasts`, 방송 아카이브, 자막과 `speech_analyses`.
- `product_summaries`, `sales_weekly` 기반 내부 데이터.
- Research 합성과 방송 컨텍스트 조회.
- Screenplay 생성, 버전 관리, 컴플라이언스 검수, 카테고리 패턴 주입.
- 사용자 피드백, `product_selections` 칸반, 승격 API와 운영 크론.
- 추천·방송·대본 관련 스모크와 회귀 테스트.

따라서 새 시스템을 별도 구축하기보다 기존 도메인 테이블과 워크플로 위에 통합 근거 계층을 추가하는 방식이 적합하다.

### 3.2 2026-08-29 점검 기준의 핵심 공백

운영 데이터와 코드 점검에서 다음 문제가 확인됐다.

- 발견 상품은 7,839건이지만 enrichment 완료와 C package 보유 상품은 각각 9건이다.
- TV evidence가 있는 발견 상품은 1,189건이며, 평가 대기 또는 오래된 상품이 상당수다.
- Discovery에서 Research로 승격된 상품은 0건이다.
- Research 결과는 12건, Screenplay는 27건이지만 제품 연결 Screenplay는 5건이다.
- 경쟁 방송 6,262건 중 음성 분석 완료는 약 50건으로 표본이 작고 특정 카테고리에 치우쳐 있다.
- 과거 방송 56,548건 중 카테고리 확인 데이터는 약 9,886건이다.
- 추천 상위 30개 중 29개가 100점인 경우가 있어 단일 점수의 변별력이 부족하다.
- 추천 피드백 표본이 없어 학습 로직은 cold start 상태다.
- 파이프라인 상단 Sankey는 `lib/pipeline/data-intelligence-graph.ts`의 정적 `current/planned` 정의로, 실제 DB 준비 상태와 동일하지 않다.
- `product_selections`는 `sourced` 피드백에 의해 생성되는 운영 상태이며 데이터 인텔리전스의 완성도를 나타내지 않는다.
- `lib/workflows/screenplay.workflow.ts`의 경쟁 방송 패턴은 `BROADCAST_INTEL_ENABLED=true`일 때만 적용되고, 비활성·표본 부족·타임아웃 시 결과에서는 패턴이 빠진 사실이 명확하지 않을 수 있다.
- 일부 CLI 경로는 통합 Screenplay 워크플로 대신 생성기를 직접 호출해 방송 패턴과 검수 경로를 우회한다.
- Research 합성은 방송 컨텍스트를 프롬프트에 사용하지만 최종 결과에서 사용 근거를 완전하게 재현할 스냅샷이 없다.

### 3.3 문제의 본질

현재 기능은 개별적으로 존재하지만 다음 공통 계약이 없다.

- 같은 상품을 여러 소스에서 하나로 식별하는 계약.
- 수치·주장·대리 신호·추론을 구분하는 근거 계약.
- 추천과 대본이 어떤 근거를 사용했는지 보존하는 계약.
- 저장 데이터 전용 모드와 추가 조사 모드를 강제하는 실행 계약.
- 실제 데이터 준비도를 화면에 표시하는 운영 계약.

이 설계는 이 다섯 계약을 추가해 기존 기능을 하나의 데이터 인텔리전스 시스템으로 만든다.

## 4. 목표와 비목표

### 4.1 목표

- QVC Japan, Shop Channel, OA의 상품·방송 데이터를 지속적으로 축적한다.
- 원본 출처와 확인 시점을 잃지 않고 상품과 방송을 연결한다.
- 경쟁사 실제 매출을 알 수 없는 상황에서도 공개 근거의 성격을 정직하게 표시한다.
- 저장된 근거만으로 제품 후보를 검색하고 비교할 수 있다.
- 사용자 선택 시에만 부족한 근거를 외부에서 보강한다.
- 자사 상품 엑셀을 선택적으로 받아 자사 적합도와 수익성 판단을 개선한다.
- 경쟁 방송의 구조·시연·FAQ·판매 언어 패턴을 상품별 대본에 활용한다.
- 추천과 대본의 주요 판단을 출처까지 재현할 수 있다.
- 파이프라인 화면에서 실제 수집·정규화·분석 준비도를 확인할 수 있다.

### 4.2 비목표

- 신규 경쟁사나 신규 마켓플레이스 수집기 추가.
- 경쟁사의 비공개 실제 매출·판매수량 추정치를 사실로 제공.
- 모든 56,000여 건의 과거 방송을 즉시 전사·분석.
- 제품 후보를 자동 승격하고 Research·Screenplay를 자동 생성.
- 공급사 발주, 재고, 물류, 정산 시스템 구축.
- 클릭과 저장 행동을 실제 판매 성공으로 간주하는 자동 학습.
- 현재 `product_selections` 칸반을 삭제하거나 기존 운영 프로세스를 강제 중단.

## 5. 핵심 용어

- **원본 관측(raw observation):** 소스에서 특정 시점에 확인한 변경 전 데이터.
- **표준 상품(canonical product):** 여러 소스의 상품 레코드를 연결하는 내부 상품 정체성.
- **근거(evidence):** 주제에 대한 하나의 확인 가능한 사실, 주장, 대리 신호 또는 추론.
- **근거 유형(evidence class):** `verified`, `source_claim`, `proxy`, `inferred`, `internal_input`.
- **인사이트 스냅샷(insight snapshot):** 특정 시점의 근거를 집계해 만든 재사용 분석 결과.
- **지식 스냅샷(knowledge snapshot):** 한 추천·리서치·대본 실행이 실제로 사용한 근거와 인사이트의 고정 목록.
- **저장 데이터 모드(stored-only):** 실행 중 외부 검색을 허용하지 않는 기본 모드.
- **추가 조사 모드(supplemented):** 사용자가 명시한 부족 항목만 외부에서 보강하는 모드.

## 6. 목표 아키텍처

### 6.1 논리 계층

```
┌──────────────────────────────────────────────────────────────┐
│ Source adapters                                               │
│ QVC Japan │ Shop Channel │ OA │ Internal Excel               │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ Observation layer                                             │
│ 원본 payload, URL, observed_at, raw hash, collection run      │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ Identity & normalization                                      │

└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ Evidence ledger                                               │

└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ Insight snapshots                                             │
│ 시장 신호 │ 경쟁 강도 │ 가격·구성 │ 방송 패턴 │ 자사 적합도 │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
       ┌───────────────────────┴───────────────────────┐
       ▼                                               ▼
┌───────────────────────┐                    ┌───────────────────────┐
│ On-demand product find│                    │ On-demand screenplay  │
│ 근거 기반 비교·추천   │                    │ 구조·장면·대본·검수   │
└───────────────────────┘                    └───────────────────────┘
```

### 6.2 자동화 경계

백그라운드 작업은 Observation부터 Insight snapshot까지에서 끝난다. 제품 추천 실행, 상세 Research 실행, Screenplay 생성은 백그라운드 잡의 후속 단계가 아니다.

`product_selections`와 Discovery → Research 승격 기능은 운영자가 선택한 후 사용할 수 있는 별도 기능으로 유지할 수 있지만, 다음 의미를 갖지 않는다.

- 파이프라인이 정상 작동하려면 선택 건수가 1건 이상이어야 한다.
- 발견 상품이 자동으로 승격되어야 한다.
- 승격 후 Research와 Screenplay가 자동 생성되어야 한다.

## 7. 데이터 모델

기존 도메인 테이블은 유지한다. 다음은 신규 논리 엔터티이며, 구현 계획에서 기존 테이블 확장 또는 신규 테이블 중 하나를 선택한다.

### 7.1 표준 상품과 소스 링크

**`canonical_products`**

- `id`
- 표준 상품명, 브랜드, 모델명, 표준 카테고리
- 정규화 속성 JSON
- 활성·병합 상태
- 생성·수정 시점

**`product_source_links`**

- `canonical_product_id`
- 소스 유형과 원본 테이블·레코드 ID
- 소스 상품 ID와 원본 상품명
- `match_method`: exact ID, normalized key, similarity, manual
- `confidence`
- 자동 제안인지 사용자 확인인지
- 확인자와 확인 시점

원칙:

- 낮은 신뢰도의 유사도 매칭은 자동 확정하지 않는다.
- 한 번 확인한 별칭과 소스 연결은 재사용한다.
- 잘못된 연결을 병합 해제할 수 있어야 한다.
- 일본어 상품명은 NFKC, 전각·반각, 가나 변형, 브랜드 접두를 고려한다.

### 7.2 근거 원장

**`evidence_items`**

- 주제 유형과 주제 ID: 상품, 방송, 카테고리, 회사 상품 등
- `predicate`: price, airing_count, review_count, seller_claim_units 등
- 값 JSON과 단위
- 적용 기간과 관측 시점
- `evidence_class`
- 소스 유형, 소스 레코드, URL
- 원본 payload hash 또는 원본 위치
- 신뢰도, 유효기간, 현재 상태
- 충돌 그룹과 대체한 이전 근거

근거 유형:

| 유형 | 의미 | 예시 |
| --- | --- | --- |
| `verified` | 직접 확인되거나 공식성이 높은 사실 | 방송 날짜, 표시 가격, 공식 공시 수치 |
| `source_claim` | 제조사·판매자·방송이 주장한 값 | “누적 100만 개 판매” |
| `proxy` | 수요를 간접적으로 보여주는 값 | 방송 횟수, 리뷰 증가, 순위, 품절 |
| `inferred` | 규칙·통계·모델이 계산한 해석 | 시장 모멘텀, 경쟁 강도 |
| `internal_input` | 자사 업로드 또는 운영자 확정 값 | 자사 원가, 상품 속성, 실제 이익 |

`unknown`은 근거 유형이 아니라 값 상태다. 값이 없음을 0으로 저장하거나 계산하지 않는다.

### 7.3 인사이트 스냅샷

**`insight_snapshots`**

- 인사이트 유형과 대상 상품·카테고리
- 입력 기간과 데이터 cutoff
- 결과 JSON
- 입력 근거 수와 근거 ID 집합 또는 연결 테이블
- 계산식 버전, 모델·프롬프트 버전
- 생성 시점, 유효기간, 신뢰도
- 데이터 커버리지와 부족 항목

대표 인사이트:

- 상품 방송 빈도와 변화.
- 카테고리 가격·구성 분포.
- 경쟁 상품 밀도와 반복 등장.
- 판매 관련 공개 신호.
- 방송 구성, 시연, FAQ, 반론 처리, 판매 언어 패턴.
- 자사 데이터가 있을 때의 카테고리·가격대·속성별 수익성.

### 7.4 지식 스냅샷

**`knowledge_snapshots`**

- 소비 유형: product recommendation, research, screenplay.
- 실행 ID와 사용자 ID.
- 모드: `stored_only` 또는 `supplemented`.
- 검색 조건과 데이터 cutoff.
- 생성 시점.
- 사용한 모델·점수 계산 버전.

**`knowledge_snapshot_items`**

- snapshot ID.
- evidence 또는 insight ID.
- 사용 역할: candidate retrieval, ranking, product fact, market context, script pattern 등.
- 결과의 어느 항목 또는 대본 구간에 사용했는지.

추천·대본을 다시 열었을 때 같은 지식 스냅샷으로 당시 판단을 설명할 수 있어야 한다.

### 7.5 수집 실행과 작업 상태

**`data_pipeline_runs`**

- 소스, 작업 유형, 실행 ID.
- 시작·종료·마지막 heartbeat.
- 상태: queued, running, succeeded, partial, failed.
- cursor와 대상 범위.
- 신규·갱신·중복·실패 건수.
- 오류 코드와 요약.
- 마지막 시도와 마지막 성공 시점을 분리.

필요 시 레코드 단위 실패 큐를 별도 관리한다. 반복 실패가 전체 수집을 막지 않아야 한다.

### 7.6 엑셀 업로드

**`import_batches` / `import_rows`**

- 원본 파일 메타데이터와 해시.
- 열 매핑과 매핑 버전.
- 행별 검증·상품 연결 결과.
- 반영·부분 반영·취소 상태.
- 업로드 사용자와 시점.

최소 허용 입력은 상품 기본정보다. 성과·비용 열은 있을 때만 근거로 변환한다.

## 8. 백그라운드 데이터 파이프라인

### 8.1 단계

1. **수집** — QVC, Shop Channel, OA의 원본과 변경을 저장.
2. **중복 제거·버전 확인** — raw hash와 소스 키로 멱등 처리.
3. **정규화** — 브랜드, 이름, 가격, 카테고리, 방송 시각 정리.
4. **상품·방송 연결** — 확정 ID 우선, 유사도는 제안, 애매하면 검토 큐.
5. **방송 분석** — 자막·음성에서 구간, 소구점, FAQ, 시연, 증거 표현 추출.
6. **근거 변환** — 원본 관측을 근거 유형별 atomic record로 변환.
7. **인사이트 증분 갱신** — 새 근거가 영향을 주는 상품·카테고리만 재계산.
8. **품질 검사** — 최신성, 분류율, 연결률, 편중, 실패 상태 갱신.

### 8.2 방송 분석 우선순위

전체 과거 방송의 일괄 분석 대신 다음 순서를 사용한다.

1. 최근 방송과 신규 상품.
2. 반복 방송·재입점 상품.
3. 온디맨드 검색에서 자주 조회되는 카테고리.
4. 분석 표본이 부족한 카테고리.
5. 사용자가 대본을 만들려는 상품과 유사한 방송.
6. 나머지 역사 데이터 백필.

작업 큐는 카테고리별 최소 표본과 최대 편중 비율을 고려한다. 현재처럼 기본값 하나에 분석이 집중되는 동작을 피한다.

### 8.3 최신성

소스와 근거 종류에 따라 유효기간을 다르게 둔다.

- 방송 편성·가격·구성: 짧은 최신성.
- 상품 속성·브랜드: 중간 최신성.
- 과거 방송 구조와 언어 패턴: 긴 최신성.
- 자사 업로드: 사용자가 제공한 기준 기간을 따름.

오래된 근거는 삭제하지 않고 `stale` 상태로 남긴다. 기본 모드에서도 참고할 수 있지만 결과에 오래됐음을 표시한다.

## 9. 온디맨드 제품 찾기

### 9.1 입력

- 카테고리 또는 상품 용도.
- 목표 고객.
- 희망 판매 가격대.
- 목표 이익 또는 마진.
- 방송에서 강조할 특성.
- 제외 조건.

모든 항목은 필수는 아니다. 입력이 부족하면 시스템은 저장된 근거 안에서 넓게 검색하되, 사용자가 제공하지 않은 비용·성과 값을 임의로 채우지 않는다.

### 9.2 처리 흐름

```
검색 요청 저장
  → 표준 상품 후보 검색
  → 근거·인사이트 묶음 조회
  → 데이터 커버리지와 신뢰도 계산
  → 항목별 평가
  → 후보 순위와 설명 생성
  → 지식 스냅샷 저장
  → 사용자에게 비교 가능한 결과 제공
```

기본 모드는 실행 경계에서 외부 네트워크 검색을 차단한다. 단순히 프롬프트에 “검색하지 말라”고 쓰는 것으로 끝내지 않는다.

### 9.3 평가 축

- 시장 수요 신호.
- 자사 상품·고객 적합도.
- 수익성 또는 수익성 판단 가능 여부.
- 경쟁 여유도.
- 방송 시연·설명 적합도.
- 데이터 신뢰도.

단일 0~100 점수만으로 설명하지 않는다. 각 축과 근거 커버리지를 함께 표시한다.

수익성 우선 규칙:

1. 자사 이익 또는 원가 기반 계산이 가능하면 예상 기여이익을 최우선 순위 신호로 사용한다.
2. 자사 성과는 있지만 비용이 없으면 매출·수량은 보조 신호로만 사용한다.
3. 자사 성과가 없으면 수익성은 `unknown`으로 유지하고 시장 기회도와 방송 적합도로 후보를 정렬한다.
4. 서로 다른 커버리지 수준의 후보를 같은 정밀도의 점수처럼 비교하지 않는다.

LLM은 확정된 후보·점수·근거를 설명한다. 후보 순위의 원천 수치나 존재하지 않는 판매량을 생성하지 않는다.

### 9.4 결과

각 후보는 다음을 제공한다.

- 추천 이유와 우리 회사와의 적합 근거.
- 확인된 경쟁사 사실.
- 판매자 주장과 대리 신호.
- 경쟁 포화도와 위험.
- 방송 적합도와 예상 시연 포인트.
- 사용한 출처, 확인 날짜, 최신성, 신뢰도.
- 부족한 데이터와 추가 조사 제안.

### 9.5 후속 행동

- 관심 상품으로 저장.
- 제외하고 이유 기록.
- 상세 Research 실행.
- 부족한 항목 추가 조사.
- 대본 만들기로 전달.

어떤 행동도 다음 산출물을 자동 생성하지 않는다. `sourced`와 `product_selections`는 필요하면 별도의 실제 취급 운영 흐름으로 사용한다.

## 10. 선택적 추가 조사

### 10.1 명시적 실행

추가 조사는 사용자가 다음을 확인하고 실행한다.

- 무엇이 부족한지.
- 어떤 항목을 조사할지.
- 조사 결과가 추천 또는 대본을 어떻게 바꿀 수 있는지.

버튼 한 번으로 모든 항목을 전체 재검색하는 방식보다 상품 사실, 가격, 판매 주장, 리뷰 신호 등 부족 항목 단위로 실행한다.

### 10.2 저장 규칙

- 검색 결과 URL, 제목, 확인 시점, 발췌 위치를 보존.
- 공식 정보, 판매자 주장, 제3자 기사, 대리 신호를 구분.
- 기존 근거와 충돌하면 둘 다 보존하고 충돌 상태로 표시.
- 새 근거를 반영한 새 insight/knowledge snapshot 생성.
- 조사 전후 결과의 변경점을 표시.

실패하거나 결과가 없더라도 기존 저장 데이터 기반 결과는 유지한다.

## 11. 경쟁 방송 인사이트 기반 대본

### 11.1 시작점

- 추천 결과에서 선택한 상품.
- 엑셀로 등록한 자사 상품.
- 직접 입력한 신규 상품.
- 기존 Research 상품.

모든 경로는 하나의 Screenplay application workflow로 수렴한다. CLI, API, UI가 생성기를 직접 우회 호출하지 않는다.

### 11.2 단계

1. **상품 근거팩** — 확인된 사실, 판매자 주장, 차별점, 가격·구성, 미확인 항목, 금지 표현.
2. **유사 방송 검색** — 카테고리뿐 아니라 상품 유형, 용도, 가격대, 고객, 시연성, 방송 길이, 진행 구조를 사용.
3. **패턴 선택** — 오프닝, 문제 제기, 시연, 가격 공개, FAQ, 반론, 클로징 패턴.
4. **방송 구성안** — 메시지 순서와 구간 길이.
5. **장면·시연 계획** — 진행자 행동, 카메라·상품 클로즈업, 전후 비교, 증거 제시.
6. **초안 대본** — 상품 근거와 선택한 패턴을 입력으로 생성.
7. **검수** — 상품 사실, 금지·과장 표현, 근거 연결, 경쟁사 문구 복제 여부 확인.
8. **버전 저장** — 지식 스냅샷, 패턴 스냅샷, 모델·프롬프트와 함께 저장.

### 11.3 참고 방송의 사용 원칙

가져올 것:

- 메시지 배치와 구간 순서.
- 시연 타이밍.
- 가격·구성 공개 방식.
- 고객 질문과 반론 처리 유형.
- 구매 결정을 돕는 증거 제시 방식.

가져오지 않을 것:

- 경쟁사 고유 문장과 캐치프레이즈.
- 검증되지 않은 효능·판매량.
- 브랜드 고유 스토리.
- 근거 없는 최상급 표현.

### 11.4 근거 부족 처리

- 상품 사실 부족: `[확인 필요]` 또는 표현 제외.
- 참고 방송 표본 부족: 일반 구조 사용 사실과 표본 수 표시.
- 패턴 기능 비활성·타임아웃: 결과에 명시적인 상태를 저장하고 표시.
- 추가 조사가 필요하면 사용자에게 범위를 제안하되 자동 실행하지 않음.

`BROADCAST_INTEL_ENABLED` 같은 플래그가 필요하더라도 조용히 빈 패턴으로 처리하는 것이 아니라 `disabled`, `under_sampled`, `timed_out`, `failed`, `applied` 상태를 결과와 운영 화면에 남긴다.

### 11.5 편집 학습

- 사용자가 삭제한 표현, 추가한 장면, 선택한 소구점과 최종 승인 버전을 저장.
- 모든 임시 수정을 정답으로 학습하지 않는다.
- 최종 승인된 버전만 향후 구성 추천의 참고 후보로 사용한다.

## 12. 파이프라인과 기능 화면

### 12.1 파이프라인 화면

정적 `current/planned` Sankey를 실제 상태 조회 기반 화면으로 전환한다.

**데이터 준비 상태**

- 오래된 근거와 실패 대기열.

- 상품·카테고리별 근거량.

추천 또는 대본 실행 건수가 0이어도 사용자가 요청하지 않았다면 파이프라인은 정상일 수 있다.

## 13. 오류 처리와 데이터 품질

### 13.1 수집

- 작업은 멱등적이어야 한다.
- 일시 오류는 제한된 횟수로 재시도한다.
- 반복 실패는 실패 대기열로 이동한다.
- 일부 소스 실패가 다른 소스를 막지 않는다.
- 실패·빈 결과·변경 없음은 서로 다른 상태다.
- 실패 데이터로 기존 정상 데이터를 덮어쓰지 않는다.
- 소스 구조가 바뀌어 파싱이 깨지면 0건 성공으로 기록하지 않는다.

### 13.2 값 상태와 충돌

- `0`, `unknown`, `not_applicable`, `stale`, `conflicting`을 구분한다.
- 최신이라는 이유만으로 낮은 신뢰도 값을 공식 값 위에 덮어쓰지 않는다.
- 상충 근거를 모두 보존하고 계산에 선택한 값을 기록한다.
- 시스템 추론을 원본 사실로 승격하지 않는다.

### 13.3 엑셀

```
업로드 → 열 자동 인식 → 사용자 매핑 확인 → 검증 미리보기
       → 상품 연결 확인 → 최종 반영 → 필요 시 배치 취소
```

- 중복 파일과 중복 행을 탐지한다.
- 오류 행만 분리해 사유를 제공한다.
- 자동 상품 연결은 반영 전 확인 가능해야 한다.
- 원본 파일과 매핑 버전을 보존한다.
- 취소는 해당 배치가 추가한 근거를 비활성화하며 과거 감사 기록은 보존한다.

### 13.4 생성 작업

- 구조화 출력 스키마를 검증하고 제한적으로 재시도한다.
- 부분 생성물을 최종본으로 표시하지 않는다.
- 근거 없는 판매량·효능·최상급 표현은 차단하거나 확인 필요로 남긴다.
- 모델, 프롬프트, 입력 스냅샷과 오류 상태를 저장한다.
- 저장 데이터 모드에서 외부 검색 도구를 실행하려는 시도는 정책 오류로 실패시킨다.

---

## 14. 보안과 접근 제어

- 기존 인증 역할과 RLS 원칙을 유지한다.
- 엑셀 원본 파일은 서비스 역할만 읽을 수 있는 비공개 저장소에 둔다.
- 사용자별 업로드, 수정, 조사 실행, 최종 승인 기록을 감사 로그에 남긴다.
- 외부 검색 결과에서 받은 HTML·텍스트는 명령이 아니라 비신뢰 데이터로 처리한다.
- URL fetch는 허용 프로토콜, 리다이렉트, 사설 네트워크 차단 등 기존 Research 보안 정책을 재사용한다.
- UI에 보여줄 발췌와 모델 프롬프트 입력을 분리하고 필요한 길이만 사용한다.

## 15. 품질 기준

초기 운영 게이트:

- 최근 활성 상품의 카테고리 분류율 95% 이상.
- 생성 인사이트의 원본 근거 연결률 100%.
- 추천 결과의 출처·확인 날짜·신뢰도 표시율 100%.
- 대본의 검증 가능한 주요 주장 근거 연결률 100% 또는 명시적 `[확인 필요]`.
- 저장 데이터 모드의 무단 외부 검색 0건.
- 정보 없음이 숫자 0으로 계산되는 사례 0건.
- 수집 작업에서 실패와 빈 결과를 성공으로 기록하는 사례 0건.
- 특정 카테고리 분석 편중과 표본 수가 운영 화면에 100% 노출.

단일 추천 점수의 만점 비율은 지속 측정한다. 다수 후보가 같은 만점을 받으면 배포 차단 또는 점수 체계 재보정 신호로 사용한다.

## 16. 테스트 전략

### 16.1 단위 테스트

- 상품명·브랜드·카테고리 정규화.
- 일본어 변형과 동일 상품 제안.
- 근거 유형 분류.
- 0과 unknown 구분.
- stale·conflicting 처리.
- 항목별 점수와 커버리지.
- 지식 스냅샷의 불변성.

### 16.2 소스 계약 테스트

- QVC, Shop Channel, OA의 저장된 응답 fixture로 파서 검증.
- 구조 변경 시 테스트 실패.
- 빈 편성, 변경 없음, HTTP 실패, 파싱 실패 구분.

### 16.3 통합 테스트

- 수집 → 정규화 → 근거 → 인사이트.
- 엑셀 업로드 → 열 매핑 → 상품 연결 → 근거 반영 → 배치 취소.
- stored-only 추천에서 외부 검색 호출이 없는지 검증.
- supplemented 모드가 지정 항목만 검색하고 근거로 저장하는지 검증.
- 추천과 대본이 같은 지식 스냅샷 규격을 사용하는지 검증.
- 추천 상품과 직접 입력 상품 모두 통합 Screenplay 워크플로를 사용하는지 검증.

### 16.4 대본 품질 테스트

- 상품 사실과 근거 일치.
- 경쟁사 문장 장문 복제 방지.
- 선택한 방송 패턴의 실제 반영.
- 금지·과장 표현 탐지.
- 표본 부족·패턴 비활성 상태 노출.
- 구성안·장면 계획·대본·검수 결과의 버전 연결.

### 16.5 실제 E2E 시나리오

가전처럼 분석 표본이 상대적으로 많은 카테고리와 패션처럼 적은 카테고리를 각각 검증한다.

1. 현재 소스 수집 성공 확인.
2. 상품·방송·카테고리·근거 연결 확인.
3. 저장 데이터만으로 제품 검색.
4. 추천 이유, 위험, 출처, 최신성 확인.
5. 외부 검색이 호출되지 않았음을 확인.
6. 사용자가 한 후보를 관심 상품으로 저장.
7. 해당 상품으로 경쟁 방송 인사이트와 대본 생성.
8. 별도 직접 입력 상품으로도 대본 생성.
9. 주요 주장과 참고 패턴의 근거 연결 확인.
10. 동일 지식 스냅샷으로 결과 설명 재현.
11. 부족 항목 하나만 추가 조사하고 새 스냅샷과 변경점 확인.

## 17. 단계별 구축 순서

### Phase 0 — 기준 상태 고정

- 현재 테이블·크론·API·UI와 데이터 품질 지표 목록화.
- 대표 소스 fixture와 추천·대본 golden sample 확보.
- 현재 수집 성공, 카테고리 범위, 방송 분석 범위를 기준선으로 저장.

### Phase 1 — 표준 상품·근거·스냅샷

- 표준 상품과 소스 링크.
- 근거 원장.
- 인사이트·지식 스냅샷.
- 최근 활성 상품과 기존 분석 방송부터 점진적 backfill.
- destructive migration 없이 기존 테이블과 병행.

### Phase 2 — 백그라운드 파이프라인 품질

- 공통 run 상태와 실패 큐.
- 카테고리 분류 및 상품 연결 품질 개선.
- 방송 분석 우선순위·편중 제어.
- 증분 인사이트 갱신.
- 실제 상태 기반 Pipeline 화면.

### Phase 3 — 저장 데이터 기반 제품 찾기

- stored-only 실행 계약.
- 후보 검색과 항목별 평가.
- 근거·신뢰도·부족 정보 표시.
- 관심 상품 저장과 제외 이유.
- 추천 실행과 지식 스냅샷 저장.

### Phase 4 — 통합 대본 워크플로

- 모든 진입점의 단일 application workflow 통합.
- 유사 방송 검색과 패턴 상태.
- 상품 근거팩, 구성안, 장면·시연 계획.
- 대본, 컴플라이언스, 근거 연결, 버전 저장.

### Phase 5 — 선택적 추가 조사

- 부족 근거 식별 UI.
- 항목별 조사 실행.
- 근거 원장 저장과 충돌 처리.
- 조사 전후 지식 스냅샷 비교.

### Phase 6 — 엑셀과 자사 맞춤화

- 가변 열 매핑과 미리보기.
- 상품 연결 검토.
- 선택적 성과·비용 근거.
- 실제 이익 데이터가 있을 때만 수익성 우선 랭킹.

## 18. 호환성과 전환 원칙

- 기존 수집 테이블을 한 번에 대체하지 않는다.
- 기존 UI는 새 읽기 모델이 준비될 때까지 유지한다.
- 새 근거 원장은 dual-write 또는 backfill로 채운 뒤 소비 기능을 전환한다.
- `product_selections`는 실제 취급 운영 칸반으로 유지하되 데이터 인텔리전스 상태와 분리한다.
- Discovery → Research 승격 기능은 사용자가 원하는 경우 사용할 수 있지만 추천 완성 조건에서 제외한다.
- 기존 Screenplay 버전은 유지하고 새 knowledge snapshot 링크를 nullable로 추가한 뒤 신규 버전부터 필수화한다.
- 각 Phase는 feature flag와 읽기 경로 전환으로 롤백 가능해야 한다.

## 19. 완성 판정

시스템은 다음이 모두 가능할 때 이번 목표를 달성한 것으로 본다.

```
경쟁사 데이터가 백그라운드에서 지속 수집된다.
→ 상품·방송·카테고리·근거가 추적 가능하게 연결된다.
→ 사용자가 저장 데이터만으로 제품을 검색한다.
→ 추천 결과에서 사실·주장·대리 신호·추론을 구분해 확인한다.
→ 사용자가 원하는 상품만 선택한다.
→ 같은 지식 계층에서 유사 경쟁 방송과 판매 패턴을 찾는다.
→ 구성안·장면 계획·대본을 요청 시 생성한다.
→ 주요 주장과 참고 패턴의 출처를 검증한다.
→ 사용자가 선택한 경우에만 부족한 항목을 추가 조사한다.
→ 결과와 당시 사용한 지식 스냅샷을 재현한다.
```

추천·Research·Screenplay가 자동으로 연쇄 생성되는 것은 완성 조건이 아니며 오히려 승인된 운영 경계를 위반한다.

## 20. 구현 계획에서 확정할 기술 세부사항

다음은 제품 결정이 아니라 구현 세부사항이므로 후속 구현 계획에서 코드와 마이그레이션 단위로 확정한다.

- 논리 엔터티를 신규 테이블로 둘지 기존 테이블을 확장할지.
- evidence predicate 사전과 JSON schema.
- 표준 상품 자동 매칭 임계값과 운영자 리뷰 UX.
- 인사이트별 유효기간과 재계산 트리거.
- 추천 항목별 정규화 방식과 동률 처리.
- 대본 구간별 claim-to-evidence 연결 표현.
- 과거 데이터 backfill 배치 크기와 운영 시간대.
- 엑셀 원본 보존 기간과 취소 구현 방식.

이 문서가 승인되면 `superpowers:writing-plans` 절차로 Phase 0부터 세부 구현 계획을 작성한다.
