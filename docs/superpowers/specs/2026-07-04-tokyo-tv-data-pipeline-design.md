## 1. 문제 정의

### 1.1 입력의 성격 (확정)

파이프라인의 입력은 **정제된 스키마가 아니라 날것의 업무 파일**이다. 데이터 요청서(`tokyo_tv_data_request_2026-07-04`)를 통해 받게 되는 것은:

- 형식을 예측할 수 없음: 엑셀·워드·PDF·종이 스캔·화면 캡처가 혼재.
- 상대는 AI/데이터 전문가가 아니며, 우리는 상대 데이터가 어떻게 정리돼 있는지 사전에 알 수 없다.
- 처음엔 **샘플(1~3개월분/대본 10본 등)**로 오고, 이후(STEP 3 히어링 후) 범위가 확대되는 지속 피드로 전환.

### 1.2 목적지의 비대칭 (핵심 전제)

| | ④ 대본 + 考査 | ⑤ 콜센터 AI |
|---|---|---|
| 현재 상태 | `lib/screenplay/` 엔진이 **이미 가동 중** | 코드베이스에 **아무것도 없음 (그린필드)** |
| "완성" 방식 | **코퍼스 주입** (엔진 재사용, 도쿄TV 콘텐츠로 채움) | **신규 구축** (연결 레이어 위에 새로 얹음) |
| 리스크·속도 | 낮음·빠름 (초기 데모 가능) | 높음·느림 |

**두 시스템 모두 STAGE 0~3(수집→추출→검수→연결)을 공유한다.** 따라서 파이프라인은 한 번의 투자로 두 시스템을 동시에 여는 지렛대이며, 이 문서가 여기에 집중하는 이유다.

## 2. 확정된 설계 결정

1. **완성의 정의 = 데이터 정제·연결 파이프라인** (두 시스템의 공통 토대). 최종 통합 아키텍처가 아님.
2. **변환 방식 = 하이브리드** — LLM(Gemini) 추출 + 운영자 확인. 기존 코드베이스의 "Gemini Vision 추출 + 사람 승인" 패턴과 일치.
3. **연결 전략 = 다층 매칭 + 운영자 폴백** — 정확 ID → 이름 유사도 → 시간창 → 애매하면 운영자 확인. 완벽한 entity resolution을 앞단에서 강제하지 않고 점진적으로 붙인다.
4. **저장 이원화** — 코퍼스·자산 데이터는 기존 ④ 엔진 테이블 재사용, 운영 기록 데이터는 신규 `tt_` 웨어하우스.
5. **테넌시 = 즉시 결정 (이연 불가).** 재사용 엔진(`compliance_rules`/`compliance_references`/`screenplays`)에는 현재 테넌트 스코핑이 전무하다 — 로드 함수가 `.eq("active",true)`만 건다(`check.ts:26-50`). 도쿄TV 콘텐츠를 시드하면 mediaworks 자체 검수를 오염시키므로, **재사용 테이블에 `tenant` 컬럼 추가(NOT NULL, 기존 행 기본값 `'mediaworks'`) + 두 로드 함수·문체 로더에 스레딩 + RLS로 강제**한다(잊은 필터가 누출로 이어지지 않도록 — CLAUDE.md의 "RLS는 최후 방어선" 원칙). 별도 배포/DB는 엔진을 이중 운영하게 되어 과함. `tt_` 운영 웨어하우스는 이미 물리 분리(버킷 B)라 대상 아님. **버킷 A 재사용은 이 결정에 의존한다.**
6. **④ 완성 = "코퍼스 주입 무코드"가 아니라 유계 코드 워크스트림.** (초판의 "무코드" 주장은 architect 리뷰에서 반박됨 — §6.1.) 시드만으로 끝나지 않고 선행 코드 작업이 있다: 법령 축 확장(`law` CHECK 마이그레이션 + 판정 프롬프트), 테넌트 스코핑(위 5), B-5 텔롭·가격표시 검수 경로/축, B-1 문체 주입점(테넌트별). 여전히 ⑤(그린필드)보다 빠르지만 제로코드는 아니다.

## 3. 파이프라인 골격 (5단계)

```
[STAGE 0] 수집·보관        [STAGE 1] 추출         [STAGE 2] 검수·확정
날것 파일 안전 반입    →   Gemini가 소스별      →   운영자가 원본 옆에서
원본 불변 보존             목표 스키마로 1차 추출     교정·확정 (→ 재사용 템플릿)
PII 마스킹 체크포인트       신뢰도+출처 부착           고위험(매출·考査)은 필수 확인
                                                            │
                                                            ▼
              [STAGE 4] 소비              [STAGE 3] 연결
        ④ 考査 코퍼스 주입 ← ← ←     정확ID → 이름유사도 → 시간창
        ⑤ 방송×콜×EC 예측 ← ← ←     → 애매하면 운영자 확인
                                       확정 링크 = 크로스워크 테이블
```

- **STAGE 0 수집·보관** — 보안 드롭존. 원본은 불변 보존(매출·考査는 재현·감사 가능해야 함 — 기존 `ReferenceSnapshot` 재현성 패턴과 동일 철학). 반입 시점 PII 마스킹 체크. 각 파일에 소스 유형 태그(체크리스트 A-1..C-4).
- **STAGE 1 추출** — Gemini가 파일을 읽어 소스 유형별 목표 스키마로 JSON 초안 생성. **신뢰도 + 출처(파일/셀/페이지)** 부착. 초안일 뿐.
- **STAGE 2 검수·확정** — 운영자가 원본과 나란히 교정·확정. 교정이 **그 소스의 재사용 매핑 템플릿**이 됨 → 동일 소스 다음 파일은 자동 추출 정확도↑·리뷰↓. 고위험(매출·考査) 필수 확인, 저위험은 임계값 이상 자동 통과. **단, 템플릿은 소스별×레이아웃별로 관리한다 — 스캔 PDF·병합셀 엑셀은 레이아웃 드리프트로 템플릿이 깨지므로, 소스 유형별 골든 픽스처 회귀로 검증하고 리뷰 부하의 단조 감소를 약속하지 않는다.**
- **STAGE 3 연결** — 확정 레코드를 다층 매칭으로 교차 연결. 확정 링크는 크로스워크 테이블로 영속(§5).
- **STAGE 4 소비** — ④·⑤가 연결 레이어를 소비해 완성에 도달(§6).

## 4. STAGE 1 목표 데이터 모델

### 4.1 두-버킷 원칙

- **버킷 A — 코퍼스·자산 데이터** (考査 규칙, 과거 대본, 상품 근거) → **기존 ④ 엔진 테이블 재사용**. `screenplays` / `compliance_rules` / `compliance_references`는 범용이라 도쿄TV 콘텐츠로 채우기만 함(+테넌트 태그).
- **버킷 B — 운영 기록 데이터** (방송·상품·매출·콜·EC) → **신규 `tt_` 웨어하우스**. 기존 `broadcasts`는 경쟁사 스크래핑 전용 의미(카테고리 화이트리스트 게이트·영상 아카이브·reconciliation)라 도쿄TV 자사 기밀 운영데이터와 섞으면 안 됨. 별도 테넌트·RLS·보존정책.

크로스워크(STAGE 3 산출물)가 두 버킷을 잇는다 (예: 방송 → 그때 쓴 대본 → 그 대본의 考査 결과).

### 4.3 `product_ref`는 "날것 그대로" 원칙

A-1·A-3에서 추출하는 `product_ref`는 파일에 적힌 문자열 그대로(이름이든 번호든)이며 **아직 해석하지 않는다.** 정규 상품 ID로의 해석(identity resolution)은 STAGE 3에서만 일어난다. 이 분리가 중요한 이유: 추출 단계가 성급히 추측하지 않고 "파일이 문자 그대로 뭐라고 하는지"만 정직하게 담게 만든다. 추측은 사람이 확인하는 STAGE 3으로 미룬다.

## 5. STAGE 3 연결 (다층 매칭)

연결은 성격이 다른 하위 문제 4개이며, 다층 매칭은 그 중 **상품 신원 해석**에 적용되고 나머지는 이를 앵커로 파생된다.

### 5.1 상품 신원 해석 — 4단 사다리

`product_ref` 문자열 → 정규 `canonical_product_id`:

```
Layer 1  정확 매칭      product_ref == product_no            → 자동 확정 (주 경로)
Layer 2  이름 유사도    문자 n-gram(bi/tri) · NFKC정규화 ·     → 中신뢰 제안만 (자동확정 금지)
                        가나폴딩 · 브랜드 사전
Layer 3  시간창         상품 핸들이 없는 기록은                → "이 시각에 방송된 것"으로 후보
Layer 4  운영자 확인    애매한 건 리뷰 큐 → 확정 (핵심 경로)   → match_method='manual'
```

**일본어 주의 (architect 리뷰):** 기존 `/api/selections/match-broadcast`의 Jaccard는 `tokenize()`가 **공백·문장부호로 분할**해 공백 없는 일본어 상품명을 ~1토큰으로 붕괴시킨다 → 사실상 정확매칭으로 퇴화. 게다가 auth-gated HTTP 라우트라 import 불가. 따라서 그 엔드포인트는 **사다리의 형태(suggestions/others 분리 UX)만 재사용**하고, 실제 매처는 문자 n-gram으로 신규 구현한다. 漢字/가나/全角半角 변이와 브랜드 접두를 흡수하려면 NFKC 정규화 + 가나 폴딩 + 브랜드 사전이 전제. **product_no 정확매칭(Layer 1)을 주 경로로, 운영자 확인(Layer 4)을 핵심으로 두고, Layer 2 자동확정은 하지 않는다.**

### 5.2 크로스워크 = 테이블 2개

성격이 달라 하나로 뭉치지 않는다.

- **`tt_product_aliases`** — *학습되는 신원 기억*: (raw_ref, source_type, canonical_product_id, match_method, confidence, confirmed_by, confirmed_at). 한 번 확정되면 재질문하지 않음. STAGE 2의 템플릿 학습과 같은 원리를 신원에 적용.
- **`tt_broadcast_links`** — *이벤트 링크*: (broadcast_id, linked_type[sale/callslot/ecslot/screenplay], linked_id, match_method, confidence). 방송이 무엇과 이어지는지.

### 5.3 정직한 한계 — 집계 vs 레코드

| 링크 | 소스 입도 | 연결 방식 | 정밀도 |
|---|---|---|---|
| 방송 ↔ 매출(A-3) | 레코드 단위 | 해석된 상품 + 시간 | 정확 |
| 방송 ↔ 콜/EC(C-1/C-3) | **시간대 집계** | **시간창만** | 슬롯 단위 |

콜·EC 집계는 시간대 단위라 개별 상품에 귀속시킬 수 없다. 한 슬롯에 상품 1개면 깔끔하지만 여러 개면 그 슬롯의 콜은 **"공유 귀속"으로 표시**하고 거짓 정밀도를 만들지 않는다. (코드베이스의 "silent cap 금지" 원칙과 동일 태도.)

### 5.4 신뢰도·큐·무손실

모든 링크는 match_method + confidence를 가진다. 정확·高유사도는 자동 확정, 中신뢰는 운영자 배치 리뷰 큐, 低/무매칭은 **조용히 버리지 않고 미해결로 플래그**(나중에 소스가 더 오면 재시도).

### 5.5 페이오프 쿼리

크로스워크가 생기면 `"이 방송의 매출·콜은?"` = `tt_broadcasts` → (aliases로 상품 해석) → `tt_sales` + (시간창) → `tt_call_stats`/`tt_ec_stats` 조인. 이것이 완성 판정 #2(§7). ⑤의 **"방송 → 콜+EC 통합 수요 곡선"**이 여기서 처음 계산 가능해진다(방송이 콜·EC 양쪽에 시간으로 연결되므로).

## 6. STAGE 4 소비 + 구축 순서

### 6.1 ④ 대본 + 考査 — 코퍼스 주입 + 유계 코드 (초판 "무코드" 수정)

| 받은 것 | → 들어가는 곳 | 효과 |
|---|---|---|
| B-2 考査 지적 사례 | `compliance_rules` 신규 행 (before/after → pattern+safe_rewrite) | 검수기가 **도쿄TV 심사관이 실제로 잡는 것**을 잡게 됨 (캘리브레이션 골드) |
| B-3 考査 기준 | `compliance_references` | 판단 근거 인용 |
| B-1 과거 대본 | 생성 프롬프트의 스타일 예시 | "그 집 문체"로 생성 |
| B-4 상품 근거 | facts축 그라운딩 (크로스워크로 상품 연결) | 산지·등급 주장의 근거 검증 |
| B-5 텔롭·가격표시 | 검수 대상 확장 | 발화 밖(가격표시·필수고지)까지 |

**정정 (architect 리뷰):** 식품 축 재편은 순수 데이터가 아니다 — 법령 축이 판정 프롬프트에 하드코딩(`check.ts:215`)이고 `law` CHECK가 식품법을 거부하므로, **시드 전에 유계 코드 작업 4개가 선행**한다:

1. `law` CHECK 확장 마이그레이션(食品表示法·特商法) + 판정 프롬프트의 축 확장.
2. 테넌트 스코핑(§2.5) — 로드 함수 2개 + 문체 로더 + RLS.
3. B-5 검수 경로 — `checkScreenplay` 입력에 텔롭·가격표시 추가 + 축 확장.
4. B-1 문체 주입점 — 현재 전역 싱글턴(`prompt.ts:8-12`)을 테넌트별 few-shot 주입으로.

그 위에서 B-2/B-3 시드가 엔진을 식품 검수기로 만든다. 즉 **"규칙 시드"가 마지막 단계이고, 그 전에 4개의 작은 코드 드롭이 있다.** 그래도 ⑤ 신규 구축보다 훨씬 가볍다.

### 6.2 ⑤ 콜센터 — 신규 구축, 단 연결 레이어 위에서

- **수요 예측 (v1, 먼저·쉬움):** `tt_broadcasts × tt_call_stats × tt_ec_stats`(전부 크로스워크로 시간 연결) → 시간대별 콜+EC 예측 → 인력 제안(Erlang). 입력 테이블이 STAGE 0~3의 완전한 산출물 — 그린필드지만 파이프라인 위에 바로 얹힘.
- **통화 분석 (Phase 3, C-4로 게이트):** 녹음/STT 있을 때만 착수. 콜 유형 분류·우수토크 → ④ 대본에 피드백(④↔⑤ 다리).
- **배정 최적화:** ~100석 규모 고려해 후순위로 강등(요청서 단계에서 이미 반영).

### 6.3 구축 순서 — 가치가 가장 빨리 나오는 시퀀스

```
결과물 1 ─ ④ 도쿄TV 톤+考査 대본 데모   ← B-1/B-2/B-3 + §6.1의 코드 4개 (STAGE 3 연결은 불필요)
결과물 2 ─ 연결된 운영 레이어 + ④ 매출인지 ← A-1/A-2/A-3   (STAGE 3 구축)
결과물 3 ─ ⑤ 수요 예측 v1              ← A + C-1/C-2/C-3
결과물 4 ─ ⑤ 통화분석 + ④↔⑤ 루프 (게이트) ← C-4 = 있음
```

**실행 가능한 결론:** 샘플이 도착하면 **처음 처리할 것은 운영 기록이 아니라 考査·대본 묶음(B-1/B-2/B-3)**이다. STAGE 3 연결이라는 어려운 작업을 건너뛰고 데모 가능한 완성에 도달한다(제안서의 "가동 중 기반 → 계약 직후 데모"와 정합). 단 제로코드는 아니며 §6.1의 코드 드롭 4개를 전제한다 — "가장 적은 기계"는 STAGE 3 생략을 뜻하지 무코드를 뜻하지 않는다.

## 7. "완성" 판정 기준

파이프라인(STAGE 0~3):
1. STAGE 0에 새 파일을 넣으면 엔지니어 개입 없이 운영자 확인만으로 연결된 조회 가능 레코드까지 흐른다.
2. 크로스워크가 `"이 방송의 매출·콜은?"`에 답한다.

시스템별:
3. **④ 완성** = B-2 홀드아웃 사례에서 엔진의 지적 ≈ 사람 심사관의 지적 (캘리브레이션 검증). ④ 코퍼스가 일반 약기법 시드가 아니라 도쿄TV 실제 考査 사례로 채워져 있고, §6.1의 코드 드롭 4개(법령축·테넌트·B-5·문체)가 선행 완료돼 있다.
4. **⑤ v1 완성** = 홀드아웃 주간에 대한 콜+EC 예측 오차가 허용 범위 내 (백테스트). 수요 예측 입력 테이블이 end-to-end로 채워져 있다.

## 8. 결정·게이트·잔여 항목

### 8.1 초판 대비 확정된 것 (architect 리뷰 반영)

- **테넌시:** §2.5로 승격 — `tenant` 컬럼 + RLS. (이연 항목이 아니었음.)
- **④ 코드 범위:** §2.6 / §6.1 — 4개 유계 코드 드롭. ("무코드" 철회.)
- **일본어 매칭:** §5.1 — 문자 n-gram + 정규화. Jaccard 폐기.
- **재적재 멱등성:** 모든 `tt_` 테이블에 자연 UNIQUE 키 정의 — `tt_broadcasts(air_date,air_time,corner)`, `tt_sales(order_id)` 또는 `(order_dt,product_ref,channel)`, `tt_call_stats(date,timeslot)`, `tt_ec_stats(date,timeslot)`. 겹치는 샘플 재전송(1~3월 후 2~4월)은 upsert로 흡수하고, STAGE 0가 원본 파일 해시로 중복 반입도 차단.
- **리뷰 UI:** STAGE 2/3의 운영자 리뷰 화면은 **ja 단일 로케일**(도쿄TV 운영자 대상). 운영 주체는 우리 측 온보딩 운영자(초기) → 도쿄TV 인수인계(후속). 기존 앱의 ja/ko i18n 파이프라인과 분리.

### 8.2 STEP 3 히어링의 go/no-go (파라미터 아님 — 착수 가부를 가름)

- **콜 집계 입도:** 15분 단위 확보 가부 → ⑤ 수요 예측이 상품-수준인지 슬롯-수준인지 결정(§5.3). 슬롯 단위뿐이면 ⑤ v1은 인력 배치용으로 범위 축소.
- **C-4 녹음/STT/위탁계약:** 가부 → 결과물 4(통화분석·④↔⑤ 루프) 착수 판정.

### 8.3 잔여 열린 항목 (골격 불변, 구현 시 확정)

- STAGE 0 반입 채널(업로드 UI vs 보안 전송) — 상대 IT 제약.
- STAGE 2/3 자동 통과·자동 확정 confidence 컷 — 실데이터 캘리브레이션.
- 지속 피드 크론 주기 — 초기 배치 온보딩 후 일/주 단위 결정.
- 데이터 보존정책 — NDA·개인정보 요건(요청서 §6 원칙 위에서).
- 운영 인프라(자사 SaaS vs 도쿄TV 배포) — 후속 spec.
